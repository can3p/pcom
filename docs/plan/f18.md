## F18 — Ready-made Shortcuts for iPhone and Mac

Status: planned · Depends on: the owner's Mac for signing (T1) · Branch: `feat/f18-shortcuts`

An iPhone or Mac user gets the "pcom note" and "Quote from photo" Shortcuts in a few taps: in Settings they
create a notes key, copy one setup code, tap **Add to Shortcuts**, paste the code when Shortcuts asks for
it, and the Shortcut works. Today `docs/guide/notes-on-a-phone.md` has them build each Shortcut by hand,
action by action, which few people finish and which can't be updated when pcom changes.

### What the platform allows

These constraints decide the design; each was checked before planning.

- **A Shortcut file must be signed by Apple to be imported** (iOS 15 and later, macOS 12 and later). An
  unsigned `.shortcut` is refused, and the `shortcuts://import-shortcut` scheme takes only `icloud.com`
  links.
- **Signing happens only on Apple's side**: `shortcuts sign --mode anyone` on a Mac signed into iCloud, or
  sharing from a device, which gives an `https://www.icloud.com/shortcuts/<id>` link. There is no supported
  signer on Linux. Rejected: RoutineHub's HubSign (a third party gets every file we sign and can go away)
  and `libshortcutsign`/`shortcut-sign` (needs the owner's Apple ID private key extracted onto a server).
- **So the signed file can't hold anything per user.** pcom can't sign a Shortcut with a user's key and
  URL baked in. What it can do is ship one signed Shortcut whose **import question** asks for those
  values when the user adds it: Shortcuts shows the question on the "Add Shortcut" screen, for a file and
  for an iCloud link alike.
- **One question, one paste.** The question asks for a *setup code*: the site root and the key separated by
  a space (`https://pcom.example 0190…`). The Shortcut splits it, so the same signed file works for every
  pcom instance, self-hosted ones included, and the user pastes once per Shortcut.
- **The workflow itself is a plist** (`WFWorkflow…` keys, actions by identifier such as
  `is.workflow.actions.downloadurl`). It is generated in Go from one definition, so the fields it sends are
  the ones the API test replays, and a change to the Shortcut is a reviewed diff instead of a re-recorded
  manual build.
- **One file serves iPhone and Mac.** A signed Shortcut imports on both. Actions the Mac lacks (Record
  Audio, Take Photo) are behind a **Get Device Details → Device Model** branch; what the Mac does with no
  input is open question Q-F2, settled at the T1 checkpoint.

### Behavior

- **Settings → API keys**, after a notes key is created, shows a **Set up on iPhone or Mac** block: the setup
  code with **Copy setup code**, and **Add "pcom note"** and **Add "Quote from photo"** buttons, with three
  numbered steps (copy, add, paste when asked). The key alone is still shown and copyable for scripts. The
  section's lead names the buttons even without a new key, since the Shortcuts need a fresh key to paste.
- **The buttons** open the iCloud link from config (`SHORTCUT_NOTE_URL`, `SHORTCUT_QUOTE_URL`) when set; the
  default is the owner's published links, so a self-hosted pcom needs no setup. Empty, they download the
  signed file pcom serves itself at `/shortcuts/pcom-note.shortcut` and `/shortcuts/quote-from-photo.shortcut`
  (opening it on the phone imports it).
- **The Shortcut** sends the same requests as today (`docs/api.md`, "The requests of the iPhone Shortcut")
  plus a header `X-Pcom-Shortcut: <name>/<version>`. It shows a short notification: "Saved to pcom" on
  success, pcom's `errors[0]` on a refusal, instead of the raw JSON.
- **An outdated Shortcut is told so.** When the header's version is older than the current one, the API's
  answer carries `"notice": "A newer pcom Shortcut is available: <link>"`, and the Shortcut shows it. A
  request without the header (scripts, an old hand-built Shortcut) is answered as today.
- **A setup code is a secret.** It holds the key; the Settings block says so, and the guide warns that a
  Shortcut shared onward carries its answer (checked at the T1 checkpoint: whether Shortcuts clears an
  import question's answer when a user shares the Shortcut on).

### Shared names

Defined in T0, used by every later task: package `pkg/notes/shortcut`; `shortcut.Note` and
`shortcut.Quote` (name, file name, version); `shortcut.Version` per Shortcut, an integer bumped on every
change to its plist; `shortcut.Requests`, the table of runs and their form fields; `shortcut.Header` =
`X-Pcom-Shortcut`. The files live in `pkg/notes/shortcut/files/`: `<name>.plist` (generated, golden),
`<name>.shortcut` (signed, T1), `SOURCES` (the sha256 of the plist each signed file was made from, T1).

### T0

`pkg/notes/shortcut`: the two Shortcuts as Go data, rendered to an XML plist with `encoding/xml` (no new
dependency; `plutil` converts it on the Mac in T1). Before writing the generator, get a reference: the owner
exports the hand-built "pcom note" to iCloud, and its unsigned plist (the `fields.shortcut` record of the
iCloud API) becomes `pkg/notes/shortcut/testdata/reference-note.plist`; the generator matches its action
identifiers, parameter shapes and variable attachments (`OutputUUID`, `WFTextTokenAttachment`).

Each Shortcut: a Text action holding the setup code, with a `WFWorkflowImportQuestions` entry on it
("Paste the setup code from pcom's Settings"); Split Text by space → site root and key; the requests as in
`docs/guide/notes-on-a-phone.md` today, plus the `shortcut.Header` header; Get Dictionary Value `errors` /
`notice` → Show Notification. "pcom note" also has Show in Share Sheet with Text, URLs and Images, and the
Device Model branch around Record Audio. Golden tests over both plists (`UPDATE_GOLDEN=1`), a test that
every `shortcut.Requests` field appears in the plist's form body, and `cmd/shortcuts` writing the files.
Rewrite `TestAPINotes_ShortcutRequests` (`e2e/api_notes_test.go`) to build its parts from
`shortcut.Requests`, keeping its per-run assertions. The package doc states how to change a Shortcut:
edit the definition, bump its version, regenerate, sign (T1), reshare the iCloud link, update the default.

### T1

The owner's step, with a cheap task for the tooling. `tools/sign-shortcuts.sh` (macOS only; refuses
elsewhere): `plutil -convert binary1`, `shortcuts sign --mode anyone`, check the output starts with
`AEA1` (the command can exit 0 without signing), write `SOURCES`. `make shortcuts-sign` runs it.
`TestShortcuts_SignedMatchSource` fails when a plist's sha256 differs from `SOURCES`, so a changed
definition can't ship with a stale signed file; its message names `make shortcuts-sign`.

**Checkpoint.** The owner signs, imports both files on an iPhone and a Mac, runs every row of
`shortcut.Requests` against a test instance, re-records `e2e/testdata/shortcut/*.http` if the header or a
field changed, shares both from the phone to get the iCloud links, and answers Q-F2 and the share question
in **Behavior**. The remaining tasks start after this.

### T2

`web serve --help` golden and `TestServe_EveryVariable` rows. Routes `GET /shortcuts/:file` serving the
embedded signed files (`Content-Type: application/octet-stream`, `Content-Disposition` with the Shortcut's
name; 404 for anything else), with route table rows. In `pkg/web/api_notes.go`, read `shortcut.Header`;

`pkg/notes/shortcut` (`Outdated(header string) bool`), not in the handler. Tests: the served bytes equal
the embedded file, a missing header and a current one get no notice, an old one does.

### Open questions

- **Q-F1. Setup code per Shortcut or a shared config file.** Planned: an import question on each Shortcut
  (paste twice, re-add to change the key; no file permission prompts). The alternative: the first run asks
  once and saves the code to `iCloud Drive/Shortcuts/pcom.txt`, which both Shortcuts read (one paste, a
  key can be replaced without re-adding, but a file access prompt on first run and the key in iCloud
  Drive). Recommendation: import questions.
- **Q-F2. "pcom note" on a Mac with no input.** Record Audio isn't on the Mac. Options: Dictate Text (the
  text goes as a note, no audio kept), Ask for Text, or Mac only as a share sheet / Quick Action.
  Decided at the T1 checkpoint by what the owner's Mac offers.
- **Q-F3. Whose Apple ID signs.** The signed file and the iCloud links come from the owner's Apple ID and
  are re-made on every Shortcut change. Is that acceptable, or should a separate Apple ID hold them?
