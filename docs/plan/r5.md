## R5 — bob ORM (planned)

Plan it in detail after RS lands. Known constraints:

- gogo takes no executor since v0.1.0 (R3): forms call services, and the
  mail queue is pcom's `repo.MailQueue`, which R5 converts like any other
  repository.
- After RS, every query is in `pkg/repo`. Run side by side: generate bob
  models into `pkg/model/bob` and migrate **one repository file at a time**.
  Services and handlers change only where a model type crosses the boundary
  (see Q13). Delete sqlboiler at the end. Because of ground rule 3, most test
  churn is inside `pkg/testutil/factory`, which switches to bob's generated
  factories.
- Decide Q13 (pcom-owned domain types at the repository boundary) before
  starting. If the answer is yes, R5 introduces them repository by repository,
  since the generated types change anyway.
- `make generate` and the CI freshness job from W4.S3 switch generator
  inside the same tools container. Install bob's generator in
  `tools/Dockerfile` with a pinned `ARG`, like sqlboiler: generator tools
  never enter `go.mod` (owner's decision, 2026-09-28). Keep `generate.sh`'s
  guard that the generator matches the runtime library version in `go.mod`.
- Consider `lib/pq` → `pgx` at the same time.
  - bob's psql error helpers must be generated for the driver actually used
    to connect.
  - Otherwise unique-violation detection silently never matches.
