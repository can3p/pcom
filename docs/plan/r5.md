## R5 — bob ORM

Status: planned · Depends on: — · Branch: `refactor/r5-bob`

Plan it in detail before it starts. Known constraints:

- gogo takes no executor since v0.1.0: forms call services, and the
  mail queue is pcom's `repo.MailQueue`, which R5 converts like any other
  repository.
- Every query is in `pkg/repo`. Run side by side: generate bob
  models into `pkg/model/bob` and migrate **one repository file at a time**.
  Services and handlers change only where a model type crosses the boundary
  (see Q13). Delete sqlboiler at the end. Because of ground rule 1 in `docs/testing.md`, most test
  churn is inside `pkg/testutil/factory`, which switches to bob's generated
  factories.
- Decide Q13 (below) before starting. If the answer is yes, R5 introduces
  pcom-owned types repository by repository, since the generated types change
  anyway.
- `make generate` and the CI job that checks the generated models are current switch generator
  inside the same tools container. Install bob's generator in
  `tools/Dockerfile` with a pinned `ARG`, like sqlboiler: generator tools
  never enter `go.mod` (`docs/architecture.md`). Keep `generate.sh`'s
  guard that the generator matches the runtime library version in `go.mod`.
- F7 adds repository methods. Whichever of F7 and R5 merges second converts
  or rebases them.
- Consider `lib/pq` → `pgx` at the same time.
  - bob's psql error helpers must be generated for the driver actually used
    to connect.
  - Otherwise unique-violation detection silently never matches.

### Open questions

- **Q13. Domain types at the repository boundary.** Repositories return the
  generated `core` structs to services and templates. Should they return
  pcom-owned types instead? That decouples templates and services from the
  ORM, at the cost of mapping code. Deciding before R5 matters, because bob
  changes the generated types anyway.
