## F4 — Feed pagination (planned, #124)

Today every list page loads everything: `reading.Feed` reads every post of
the direct and second-degree connections, every undismissed RSS item and
every relevant comment, merges them in memory and renders all of it;
`Explore` and `Journal` (the user page, and through `PublicFeed` the
per-user RSS feed) read every post of their kind; the private RSS feed goes
through `Feed`. Only F1's index and `/rss/public` are capped (50, no "more").

This wave pages every list with a cursor and a "Load more" button, and caps
every RSS output.

Decided by this plan (Q20 in `docs/open-questions.md` lists what the owner
should confirm; the defaults below are what the tasks build):

- **Cursor pagination, not a materialized feed table.** Each source is
  queried with `(sort_time, id) < cursor`, newest first, `limit + 1` rows;
  the service merges the sources, keeps `limit` items, and the last kept
  item is the next cursor. A materialized per-user feed is a bigger change
  (fan-out on publish, backfill) for a feed that is small per user.
- **Sort keys** stay what the feed shows today: a post's `published_at`, an
  RSS item's `user_feed_items.created_at`, a comment's `created_at`. Ties
  are broken by `(kind, id)`, so the order is total and no item is skipped
  or repeated across a page boundary.
- **The cursor** is opaque to clients: `reading.Cursor` encodes time, kind
  and id, base64url. A cursor that doesn't parse is `service.Invalid` (400),
  not the first page.
- **Page size:** `reading.PageSize = 30` items, defined once in
  `pkg/service/reading` (owner: R0). RSS outputs use F1's
  `publicPostsLimit` (50), which R0 moves into `pkg/service/reading` as
  `reading.RSSLimit` so there is one constant for every feed.
- **"Load more" button, not infinite scroll:** `hx-get` with the cursor,
  the button replaces itself (`hx-swap="outerHTML"`) with the next items
  and a new button, or nothing on the last page. Without JS it is a plain
  link to `?cursor=…`, which renders the full page starting there.
- **Scope:** `/feed`, `/explore`, `/` for anonymous visitors (F1's "load
  more" later), and the journal `/users/:username` (not in the issue, same
  unbounded load). The feed's first page alone carries the connections,
  prompts and feed token. RSS outputs (`/rss/private/:token`,
  `/rss/public/:username`, `/rss/public`) list the newest `RSSLimit` posts
  and are not paged.

### R0

Owns `pkg/repo/posts.go`, `pkg/repo/feeds.go`, `pkg/repo/comments.go`, a
new `pkg/repo/paging_test.go`, `pkg/service/reading/feed.go`,
`pkg/service/reading/reading.go`, a new `pkg/service/reading/cursor.go`,
`pkg/service/reading/feed_test.go`, `pkg/service/reading/reading_test.go`,
`pkg/web/app/routes_rss.go` and `pkg/web/app/routes_public.go` (only to
compile against the new signatures, first page everywhere) and a new
migration only if a query plan needs an index (`(user_id, published_at,
id)` on posts is the likely one; check with `explain` on the seeded
database before adding it).

- Repository methods take a `repo.Page{Before time.Time, BeforeKind,
  BeforeID string, Limit int}` (zero `Before` is the first page):
  `PublishedPostsOfUsers`, `UndismissedFeedItems`, `CommentsOnPostsNotBy`,
  `PublishedPostsByProfile` and `PublishedPostsOf`. They order by the sort
  key and id, descending. Pagination is a query with logic of its own, so
  `paging_test.go` tests it at the repository (architecture.md).
- `Feed(ctx, actor, cursor string)` returns `Items` and `Next string`
  (empty on the last page); `postsOnly` goes away: `PrivateFeed` asks the
  posts source alone for `RSSLimit`. `Explore`, `PublicPosts` and `Journal`
  take a cursor and return `Next` the same way. `PublicFeed` and the RSS
  routes use the first page of `RSSLimit`.
- Tests: two pages of each source and of the merged feed, with items that
  share a timestamp across the boundary and across sources (no gaps, no
  repeats, total order); the last page has no `Next`; a bad cursor is
  `service.Invalid`; the private feed and the per-user public feed stop at
  `RSSLimit`. The visibility rules aren't re-tested: the existing reading
  tests own them and must keep passing unchanged.

### R1

Owns `cmd/web/client/html/feed.html`, a new
`cmd/web/client/html/partial--feed-items.html`, a new
`cmd/web/client/html/partial--load-more.html`, `pkg/web/pages_reading.go`,
`pkg/web/app/routes_public.go`, `e2e/browser/feed_test.go` and
`e2e/browser/navigation_test.go` (only if it walks explore).

`feed.html` serves both `/feed` and `/explore` (`web.Feed`, `web.Explore`,
one `FeedPage`). Its item loop moves into `partial--feed-items.html`, with
the comment item exactly as it is. A request with `?cursor=…` from htmx
(`HX-Request`) renders the partial and the next button; without htmx, the
whole page from that cursor. `partial--load-more.html` is the shared button
R2 reuses. Browser test: with more than one page of items, the reader
clicks "Load more", sees the older items appended once each, and the
button disappears on the last page; explore loads a second page.

### R2

Owns `cmd/web/client/html/index.html`, `cmd/web/client/html/user_home.html`
(the post list only), `pkg/web/pages.go`, `pkg/web/pages_reading.go` (the
journal builder), `pkg/web/app/routes_public.go` (the index and journal
handlers), `e2e/browser/index_test.go`, `e2e/public_feed_test.go` and a new
`e2e/rss_limits_test.go`.

The same pattern for the anonymous index and the journal, with
`partial--load-more.html`. Browser test: the anonymous index and a journal
load a second page. E2E: `/rss/private/:token` and `/rss/public/:username`
list at most `RSSLimit` items, newest first (one case each: the cap is
R0's service test).

Cross-wave: F2 changes the feed's comment item; if F2 merges first, R1 moves
its marker into the partial unchanged. F3 adds the profile block at the
top of `user_home.html`; R2 changes only the post list below it.
