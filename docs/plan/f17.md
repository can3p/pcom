## F17 — A new post becomes a draft only when the author saves it

Status: planned · Depends on: F15 (#280) merged · Branch: `feat/f17-scratch-pad`

Today the first autosave of a new post inserts a draft, so every post the author starts and abandons
stays on the Controls page as "No subject". After this wave what the author types into a new post is still
kept as they type, on the server and so on any device, but in a **scratch pad**, not in `posts`: a draft
exists only once the author presses **Save as Draft** (or Publish). Posts that already exist, drafts or
published, autosave as they do today; this wave changes nothing about them and touches no existing row.

### Behavior

- **One scratch pad per user and prompt.** A new post written from `/write` uses the author's plain scratch
  pad; one written from `/write?prompt=<id>` uses that prompt's, so answering a prompt never overwrites the
  text started on an ordinary post. The pad holds what the form holds: subject, URL as typed, body,
  visibility and the "Email this post" choice.
- **Opening Write restores the pad.** `/write` (and `/write?prompt=`) shows the pad's text in the editor.
  The status next to the title reads **"Not saved as a draft yet · kept <time>"** instead of "Last
  Updated", without the Draft badge, while the post exists only as the pad.
- **Autosave of a new post writes the pad**, on the same triggers as today, and never mails anybody.
- **Save as Draft** creates the post from the form's text, empties the pad, and the page moves to
  `/posts/<id>/edit` as the first autosave does today. **Publish** does the same and publishes, with
  today's mails. The prompt is linked to the post at that moment, not before.
- **Discard** replaces Delete on a new post: it asks first ("Discard this text? It is not a draft and
  cannot be brought back") and empties the pad. Delete on an existing post is unchanged.
- **Preview works before the first draft.** The toolbar's preview link on a new post opens
  `/write/preview` (`?prompt=<id>` for a prompt's pad), which renders the author's own pad with the post
  page's template in edit-preview mode. It saves first, as `postform#preview` already does for a post.
- **Style review stays for drafts**: on a new post its button is disabled with the title "Available once
  saved as a draft". The grammar check works on a new post as today.
- **The author is told.** A notice above the editor of a new post, until the author dismisses it, once per
  account: "**New:** what you type here is kept as you write, on any device, but it becomes a draft only
  when you press Save as Draft. Abandoned text no longer piles up among your drafts." with **Got it**. The
  dismissal is stored per account (`user_notices`), so another browser doesn't show it again. The guide
  says the same.
- **Drafts on the Controls page show their start.** A draft without a subject is listed by the first
  `DRAFT_EXCERPT_LENGTH` (default 80) characters of its body, as plain text, instead of "No subject"; an
  empty one still reads "No subject". This helps with the drafts that exist today without changing them.

#### Two tabs or devices on one scratch pad

The pad carries a `revision` (integer, bumped by every write). The form holds the revision it last saw
in a hidden `scratch_rev` inside `#last_draft_save`, which every autosave response already replaces, so a
tab always holds the revision it wrote last.

| Save | Revision matches | Revision doesn't match (another tab or device saved since) |
|---|---|---|
| Autosave | writes the pad, bumps the revision | **conflict**: nothing is written |
| First autosave of a tab, no pad row yet | inserts the row (`scratch_rev` is 0) | another tab inserted it first: **conflict** |
| Save as Draft, Publish | creates the post from the form, empties the pad | creates the post from the form and **leaves the pad alone**: the other tab's text survives, nothing is lost |
| Discard | empties the pad | **conflict**: discarding would delete text this tab never saw |
| Keep mine (below) | writes the pad whatever its revision | — |

A post made from the pad, or a Discard, empties the row and bumps its revision rather than deleting it, and
the row records the post it became (`promoted_post_id`), so a stale tab can be told where its text went.

**What the losing tab shows.** Its autosave pauses (the form keeps only `submit` and `postform:save`
triggers until the author chooses), and the status area shows, as a `role="alert"`:

> This new post was changed on another device or tab at 14:32. The text here is no longer being saved.
> **Load the newer text** · **Keep mine** · **Save mine as a draft**

- *Load the newer text* reloads the page (the pad's text); its title warns that this tab's unsaved edits go.
- *Keep mine* saves this tab's text over the pad (`save_action=take_over`) and resumes autosave. The other
  tab then meets the same notice on its next autosave, so every overwrite is a click, never silent.
- *Save mine as a draft* is Save as Draft: a separate post, nothing lost.

When the pad was emptied since (another tab saved it as a draft, published or discarded it), the notice
reads "This text was saved as a draft in another tab" with a link to that post (from `promoted_post_id`;
"was discarded in another tab" when there is none), and offers *Keep mine* and *Save mine as a draft*.

A preview opened while the tab is in conflict shows the notice instead of opening a preview of the other
tab's text. One tab's own autosaves never conflict with each other: htmx reads the form when it sends a
request, after the previous response has replaced `scratch_rev`; T1 proves it with a burst of typing.

### T0

Migration `post_scratches`: `id uuid pk`, `user_id uuid not null references users on delete cascade`,
`prompt_id uuid references post_prompts on delete cascade`, `subject text`, `url text`, `body text not
null default ''`, `visibility post_visibility not null` (the enum of `posts.visibility_radius`), `notify_subscribers boolean`, `note_ids uuid[] not null default '{}'`,
`revision int not null default 0`, `promoted_post_id uuid references posts on delete set null`,
`created_at`, `updated_at`. Unique index on `(user_id, coalesce(prompt_id,
'00000000-0000-0000-0000-000000000000'))`, which works on any Postgres (production's version isn't pinned
in the repo; `NULLS NOT DISTINCT` needs 15). The model in `pkg/model/posts.go`; `TestModels_MatchTheSchema`
covers it. Repo methods in `pkg/repo/posts.go` (or a new `pkg/repo/scratches.go`): load by user and
prompt; insert if absent; update where revision matches, returning the new revision; empty where revision
matches; take over (update whatever the revision). Each is one statement, so concurrent tabs are decided by
the database, not by a read and a write.

`pkg/service/posts/save.go`: a save with no `PostID` goes to the pad unless its action is `save_post` or
`publish`. `SaveInput.ScratchRevision int`; a new `Action` `take_over` (valid only without `PostID`);
`Saved.Scratch *model.PostScratch` for a pad save. A conflict is `*ScratchConflict{At time.Time,
PromotedPostID string}` returned as an error (`errors.As`), not a field error. Promotion inserts the post
as today's new-post path does (prompt link, publish notifications, subscriber mail) and empties the pad
only when the revision matches.
Discard with no `PostID` empties the pad (conflict on mismatch) and keeps today's `Deleted` result.
`Scratch(ctx, actor, promptID)` loads the pad for `/write` and the preview (nil when empty); the prompt must
be one the actor may answer (`promptForRecipient`), as today. Subject, URL and body are checked by
`checkSave` against the post limits, so no new length setting is needed. DB tests in
`pkg/service/posts/save_db_test.go` (and a new `scratch_db_test.go` if clearer): one case per row of the
conflict table, a stale tab after promotion and after discard, the plain pad and a prompt's pad side by
side, no `posts` row after any number of autosaves, and deleting the user or the prompt deletes the pad.
