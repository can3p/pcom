## F6 — Public website on GitHub Pages (planned, #145)

A static site on GitHub Pages that shows what pcom does and how to run it,
built from the `docs/` folder at publish time (nothing is copied by hand),
with screenshots of the real app. After this wave, **every feature wave
ends with its user documentation and screenshots updated**; the
`wave-close` skill checks it.

**Do not start before Q24 in `docs/open-questions.md` is answered**
(generator, what is public, screenshots, address). The defaults below are
what the tasks build if the owner accepts them.

- **Sources.** Today `docs/` is developer documentation. The site publishes
  a new user-facing folder `docs/guide/` (what pcom is, connections and
  visibility, writing, the feed, RSS, comments, the API and blg,
  self-hosting) plus `README.md`, `docs/running.md` and `docs/api.md` as
  they are. Plans, history, lessons, testing and architecture stay
  unpublished. `docs/guide/` pages link to the developer docs on GitHub
  rather than repeat them; a page that would restate another file links to
  it.
- **Generator:** a small Go program, `tools/site` (its own `main`, built
  with the module's goldmark, no new toolchain), that renders a list of
  markdown files given in `docs/site.yml` (order, titles, nav) through one
  `html/template` layout into `_site/`, rewriting links between published
  files and pointing links to unpublished files at GitHub. The
  alternatives (mkdocs-material, Hugo) are Q24.
- **Screenshots** are PNGs committed under `docs/guide/screenshots/`, so
  GitHub renders the guide too. `make screenshots` produces them: a
  browser-tagged program in `e2e/browser/screenshots/` that starts the E2E
  app with the seed world (`pkg/testutil/seed`), logs in as seeded users,
  and captures a fixed list of pages at 1280×800, light theme. Each
  screenshot is named in `docs/site.yml` with the page and the seeded user,
  so a feature wave adds a row and reruns the target. No pixel diffing in
  CI: rendering varies; a CI job only checks that every image the guide
  references exists.
- **Publishing:** a workflow `.github/workflows/pages.yml`, on push to
  `master` touching `docs/**`, `README.md` or `tools/site/**`: build with
  `go run ./tools/site`, upload, deploy with `actions/deploy-pages`. Pull
  requests build without deploying, so a broken link fails the PR.
- **External, owner only:** enable Pages with "GitHub Actions" as the
  source in the repository settings; a custom domain, if any (Q24), needs
  DNS and a `CNAME`.

| Task | Tier | Owns | Depends on | Done when |
|---|---|---|---|---|
| S0 | mid | see S0 | — | `go run ./tools/site` builds `_site/` from `docs/site.yml`, its tests pass |
| S1 | mid | see S1 | — | `make screenshots` writes every PNG listed in `docs/site.yml` |
| S2 | mid | see S2 | S0, S1 | the guide pages exist, reference the screenshots, and the site builds without broken links |
| S3 | cheap | see S3 | S0 | the workflow builds on a PR and deploys on master |
| S4 | cheap | see S4 | S2 | the wave skills and the F-wave preamble require the docs update |

S0 and S1 run in parallel; S2 after both; S3 after S0; S4 last.

### S0

Owns `tools/site/` (new: `main.go`, the layout template and CSS, tests)
and `docs/site.yml` (new, with the pages and screenshots S2 will write, as
stubs). Pure Go, no database. Tests: link rewriting (published, unpublished,
anchors), a missing page or image is an error, the nav follows
`docs/site.yml`. The layout follows the app's look (Bootstrap is fine, from
a CDN), light and dark.

### S1

Owns `e2e/browser/screenshots/` (new, behind the `browser` tag), the
`screenshots` target in `Makefile`, and the PNGs under
`docs/guide/screenshots/`. Reuses `e2e/browser`'s harness and the seed; it
doesn't assert anything, so it isn't a test. Pages: the anonymous index,
a journal, a single post with comments, the feed, the editor with preview,
settings, explore. The program reads the list from `docs/site.yml`.

### S2

Owns `docs/guide/` (new pages; screenshots come from S1) and `README.md`
(a link to the site; the manifesto link to the deleted `why.md` is fixed).
Written from the code and the existing docs, not copied: each page says
what a user can do and links to the developer docs for the rest. One page
per area: overview, connections and visibility (the Q15 rules in plain
words), writing and publishing, the feed and RSS subscriptions, comments,
settings, the API and blg, self-hosting (links to `docs/running.md`).

### S3

Owns `.github/workflows/pages.yml` (new) and the check in `ci.yml` that
every screenshot `docs/site.yml` lists exists. Pin action versions as
`ci.yml` does.

### S4

Owns `.claude/skills/wave-close/SKILL.md`, `.claude/skills/wave-run/SKILL.md`,
`.claude/skills/wave-run/task_prompt.py` (the feature preamble) and
`AGENTS.md` (one row: "User documentation, the website, screenshots").
`wave-close` gains a step for F-waves: the guide pages the wave changed
are updated, new screens are added to `docs/site.yml`, `make screenshots`
is rerun, and `go run ./tools/site` builds. The F-wave template in
`docs/implementation-plan.md` (owned by the coordinator, not S4) says a
feature wave's last task is its docs task.

Cross-wave: S2 documents what is merged when it runs. A feature wave that
merges after F6 updates the guide itself (S4's rule); one that merged
before F6 is documented by S2.
