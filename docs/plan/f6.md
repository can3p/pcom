## F6 — Public website on GitHub Pages (planned, #145)

A static site on GitHub Pages, at `https://can3p.github.io/pcom/`, that
shows what pcom does and how to run it. It is built from the repository's
own files at publish time, so nothing is copied by hand, and it has
screenshots of the real app. After this wave, **every feature wave ends with
its user documentation and screenshots updated**, and `wave-close` checks
it.

Decided 2026-10-01 (Q24): **copy tommy's website**
([`can3p/tommy/website`](https://github.com/can3p/tommy/tree/main/website),
live at `can3p.github.io/tommy`). Read it before S0; its shape is the
spec:

- **Its own Go module in `website/`** (`module github.com/can3p/pcom/website`,
  goldmark only), so the generator's dependencies never touch the app's
  `go.mod` and the app's never break the site. `cd website && go run . -out
  ../site` builds it; flags `-repo` (default `..`) and `-out`.
- **The page list is Go code**, not a config file: `docPages` names each
  published file, its output path and its sidebar label. The sidebar labels
  are the only words the generator owns; every page's text comes from its
  file.
- **The landing page has no words of its own.** It renders slices of files
  that already exist: the lede and quick start from `README.md`, and one
  card per area from `docs/guide/` (title, the page's first paragraph, its
  screenshot).
- **Links are rewritten through one map** (repository path to site path). A
  link to a file the site doesn't publish goes to GitHub, and the set of
  such files is asserted by a test, so a new one is a decision rather than
  a 404 (`TestLinksToUnpublishedFilesAreKnown`). `TestEveryInternalLinkResolves`
  crawls the built site.
- **Templates and CSS are embedded** (`templates/layout.html`,
  `landing.html`, `assets/style.css`); the output gets a `.nojekyll`.
- **Publishing** is tommy's `pages.yml`: on push to `master` and
  `workflow_dispatch`, build with Go from `website/go.mod`, upload with
  `actions/upload-pages-artifact`, deploy with `actions/deploy-pages`, one
  deployment at a time without cancelling. CI builds and tests `website/`
  on every PR, so a broken link fails the PR, not the deploy.

What pcom adds to tommy's shape:

- **A user guide.** `docs/` is developer documentation today, and tommy's
  landing page leans on its provider catalogue, which pcom has no
  equivalent of. A new `docs/guide/` holds one page per area: overview,
  connections and visibility (the Q15 rules in plain words), writing and
  publishing, the feed and RSS subscriptions, comments, settings, the API
  and blg, self-hosting (a short page that links to `docs/running.md`).
  Each page says what a user can do and links to the developer docs for the
  rest, rather than repeating them.
- **What is published**, as tommy does, includes the developer docs:
  `README.md`, `docs/guide/*`, `docs/running.md`, `docs/api.md`,
  `docs/architecture.md`, `docs/testing.md`,
  `docs/implementation-plan.md`, `docs/open-questions.md`,
  `docs/lessons.md` and `docs/archive/history.md`. The wave files
  (`docs/plan/*`, transient) and `docs/gogo-extraction.md` are linked to
  GitHub.
- **Screenshots** are PNGs committed under `docs/guide/screenshots/`, so
  GitHub renders the guide too. `make screenshots` produces them: a
  browser-tagged program in `e2e/browser/screenshots/` that starts the E2E
  app with the seed world (`pkg/testutil/seed`), logs in as seeded users and
  captures a fixed list of pages at 1280×800 in the light theme. The list
  (page, seeded user, file name) is a Go table in that program. No pixel
  diffing in CI, rendering varies; the site build fails on a missing image,
  as it does on a missing page.
- **Owner only:** enable Pages with "GitHub Actions" as the source in the
  repository settings, before S3's first deploy.

S0 and S1 run in parallel; S2 after both; S3 after S0; S4 last.

### S0

Owns `website/` (new: `go.mod`, `go.sum`, `main.go`, `build.go`,
`site.go`, `markdown.go`, `templates/`, `assets/`, tests). Port tommy's
generator, dropping what is tommy-specific (the providers JSON, the plugin
and provider pages, the OpenAPI pages), and add the guide cards to the
landing page. Tests as tommy's: every internal link resolves, the
unpublished set is asserted, a missing page or image fails the build, the
landing page has a card per guide page. Until S2 lands, the guide is a
one-page stub so the build has something to render. The layout follows
the app's look, light and dark.

### S1

Owns `e2e/browser/screenshots/` (new, behind the `browser` tag), the
`screenshots` target in `Makefile` and the PNGs under
`docs/guide/screenshots/`. It reuses `e2e/browser`'s harness and the seed
and asserts nothing, so it isn't a test. Pages: the anonymous index, a
journal, a single post with comments, the feed, the editor with preview,
settings, explore.

### S2

Owns `docs/guide/` (the pages; S1 produced the screenshots) and
`README.md`: a link to the site, and a fix for the manifesto link that
still points to the deleted `why.md`. Written from the code and the
existing docs, not copied. The landing page's slices come from here and
from `README.md`, so write the first paragraph of each guide page as its
card text.

### S3

Owns `.github/workflows/pages.yml` (new, tommy's, with `main` replaced by
`master` and the build step running in `website/`) and a job in
`.github/workflows/ci.yml` that runs `go test ./...` and the build in
`website/`. Pin action versions as `ci.yml` does.

### S4

Owns `.claude/skills/wave-close/SKILL.md`, `.claude/skills/wave-run/SKILL.md`,
`.claude/skills/wave-run/task_prompt.py` (the feature preamble) and
`AGENTS.md` (one row: "User guide, website, screenshots: `website/`,
`docs/guide/`"). `wave-close` gains a step for F-waves: the guide pages the
wave changed are updated, new screens are added to the screenshot table,
`make screenshots` is rerun, and the site builds. The F-wave template in
`docs/implementation-plan.md` (the coordinator's file, not S4's) says a
feature wave's last task is its docs task.

Cross-wave: S2 documents what has merged when it runs. A feature wave that
merges after F6 updates the guide itself (S4's rule); one that merged
before is documented by S2.
