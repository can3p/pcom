## F13 — Replying by email

Status: planned · Depends on: F11, F12, a Mailjet plan with the Parse API (see Provider facts) · Branch: `feat/f13-email-replies`

People answer pcom mails with their mail client's Reply, and the answer lands on pcom:

- **A subscriber** (F11) replies to a post mail. That starts a **private email thread** with the author,
  which only the author sees on pcom. The author answers on the post page, and the answer is mailed back.
  The conversation can go on by email in both directions. Neither side ever sees the other's address beyond
  what F11 already shows the author.
- **A user with an account** replies to a comment notification. The reply becomes their comment, under
  every rule that applies to comments made on the site.

pcom doesn't receive mail today. This wave adds inbound mail with no provider types in pcom, as F12 does
for bounces and complaints.

Decided on 2026-11-05:

- **Private threads, not comments, for subscribers.** Comments are open only to the author and their direct
  connections (`docs/guide/comments.md`), and a subscriber can't read them. So a subscriber's reply goes to
  its own table, never to `post_comments`: no comment query, count, feed entry or participant mail can
  include it by accident. The subscriber mail's footer says "Reply to this mail to write to @alice. Only
  @alice reads your reply."
- **One thread per subscriber and post.** Only the author sees it, in an "Email replies" section of the post
  page under the comments. Each message shows who wrote it and when; the subscriber's messages show their
  address. The author answers with a form there and can delete the whole thread (red, asks first).
  Unsubscribing, or the author removing the subscriber, deletes that subscriber's threads. Nobody edits a
  thread message once it is sent, because the mail is already out.
- **Replies to comment notifications become comments.** This covers `post_comment_author`,
  `post_comment_participants` and their "edited" variants. A reply answers the comment the mail was about
  (`ReplyTo`). It goes through `posts.AddComment` as the user, so the usual rules hold: the user may still
  comment on the post, it isn't a draft, and the length is within `COMMENT_MAX_LENGTH`. The usual comment
  mails then go out. Replies to `new_post` follow Q-E.
- **The author can answer a thread by email too.** The author's notification about a subscriber's message,
  `author_email_reply`, has a reply address. Replying to it posts the author's answer to the thread, the
  same as the form.
- **The sender check is the token plus the `From` mailbox.** A reply is accepted only when both hold:
  - it carries a valid token;
  - the `From` address's canonical mailbox (`pgsession.CanonicalEmail`) is the one the token was issued to:
    the subscriber's, or the user's account email.

  Mailjet's Parse API posts no authentication results (see Provider facts), so pcom can't verify the sender
  beyond this. A forger needs a token, which reaches only the recipient's mailbox and mails they forward,
  and has to forge that recipient's `From` too. Mail with a Mailjet `SpamAssassinScore` at or above
  `MAIL_INBOUND_MAX_SPAM_SCORE` is dropped. Comments made from mail are marked "by email" on the page, so a
  forgery can be traced and deleted.
- **Dropped replies.**
  - **From a subscriber:** dropped silently, with no receipt mail (Q-D: no), because the sender may be
    forged.
  - **From an account user**, refused by a comment rule (too long, the post is a draft now, the connection
    is gone): they get `email_reply_not_posted`, saying why, quoting their text so it isn't lost. It goes
    to the account's own address, never to the `From` of the incoming mail, so a forged `From` can't use
    pcom to send mail anywhere else.
- **Only text is used.** pcom takes the plain-text part, or the HTML part turned into text when there's no
  plain part. The quoted original and the signature are removed. Markdown characters are escaped, so a line
  starting with `#` stays a line, in both a thread message and a comment. Attachments are dropped; the
  notification or comment says so.
- **Stored content:** thread messages and the comments made from replies. The privacy policy says that
  subscriber messages are kept until the thread, the subscription or the author's account is deleted.

### Reply address and tokens

Every mail that accepts replies has the same `Reply-To`, `REPLY_ADDRESS` (for example
`reply@reply.pcom.example`). One Mailjet parse route receives it. The mail itself says what a reply is for,
with a token in two places:

- **The subject** ends with `[ref:<token>]`. Mail clients keep the subject in a reply ("Re: …").
- **The body** ends with a muted footer line, `ref:<token>`, as plain text in both the HTML and text parts.
  Mail clients quote it in a reply.

pcom looks for the token in the subject first, then anywhere in the body, quoted parts included. It does
this before removing the quote. Mail without a token, or with more than one different token, is dropped.

The token is 16 random bytes in base32 (26 characters), and is a row in
`mail_reply_tokens (token, kind, user_id, subscription_id, post_id, comment_id, created_at)`. A token
authorizes one thing for one recipient:

| Kind | On mail | Reply becomes |
|---|---|---|
| `subscriber_post` | `subscriber_new_post` (F11) | the subscriber's message in their thread on that post |
| `subscriber_thread` | `subscriber_thread_answer` (the author's answer) | the subscriber's next message in the thread |
| `author_thread` | `author_email_reply` | the author's answer in that thread |
| `comment` | the comment mails above, per recipient | that user's reply to that comment |

- **Lifetime.** A token stops working after `REPLY_TOKEN_LIFETIME`.
- **No reply address and no token** are set when `REPLY_ADDRESS` is empty, or when a subscriber's author
  has replies off.
- **Footers** say what a reply does. Comment mails: "Reply to this mail to comment as @you."
- **`Auto-Submitted: auto-generated`** goes on every pcom mail, so a well-behaved autoresponder doesn't
  answer.
- **The token is the only secret** in a mail that accepts replies. The manage token never appears next to
  it.

### Author opt-in

`users.email_replies_enabled` (default false): "Let subscribers reply to your posts by email". It sits under
the subscriptions checkbox and is enabled only while subscriptions are. Replying to comment notifications
needs no opt-in: it only adds a way to do what the user may already do.

### Checks on an incoming mail, in order

1. **Webhook authorization**: HTTP basic auth against `MAIL_INBOUND_SECRET`, and a body cap
   (`MAIL_INBOUND_MAX_BYTES`).
2. **Automatic mail is dropped:**
   - `Auto-Submitted` other than `no`;
   - `Precedence: bulk`, `junk`, `list` or `auto_reply`;
   - `X-Autoreply` or `X-Autorespond`;
   - an empty envelope sender or `MAILER-DAEMON`;
   - a `multipart/report`.
3. **The token**, found as in "Reply address and tokens", exists and isn't expired; what it names still allows the action. For the subscriber kinds:
   the subscription is active, the author can be subscribed to and has replies on, and the post is
   published and public. For `comment`, the comment still exists.
4. **The sender**, as above.
5. **Caps for subscribers**: `SUBSCRIBER_MESSAGES_PER_SUBSCRIPTION_DAY` and
   `SUBSCRIBER_MESSAGES_PER_AUTHOR_DAY`. Account users have no extra cap, as on the site.
6. **The text** is not empty once the quote is removed; if removing it leaves nothing, the whole text is
   kept. A subscriber's message over `SUBSCRIBER_MESSAGE_MAX_LENGTH` is cut, with a note. A comment follows
   `COMMENT_MAX_LENGTH`.

Each incoming mail writes a log row, `inbound_mail_log (received_at, token_kind, outcome, drop_reason)`,
with no content, so the operator can see why a mail was dropped.

### Removing the quoted original

This is a heuristic, in a new `pkg/emailreply` (pure functions, golden tests):
- **In the plain-text part**, the reply is cut at the first of:
  - an attribution line followed by `>` lines ("On … wrote:", and the common localized forms the tests
    list);
  - a run of `>` lines that reaches the end;
  - `-----Original Message-----`;
  - an Outlook header block (`From:` … `Sent:` … `To:` … `Subject:`).

  A signature after a line that is exactly `-- ` is removed.
- **In the HTML part**, the quote elements (`div.gmail_quote`, `blockquote[type=cite]`,
  `div#appendonsend` and the Outlook divider) are removed before the HTML is turned into text with
  `github.com/inbucket/html2text`, which is already in `go.sum` as an indirect dependency.

Goldens use real replies from Gmail, Apple Mail, Outlook, Thunderbird and Fastmail, each with the personal
details replaced.

### Inbound mail without provider types

- **Mailjet sends and receives (Q-B, decided 2026-11-05).** One parse route on one address is all Mailjet
  documents, and one address is all this design needs, because the token travels in the mail.
- **In gogo** (like F12's `feedback`), an `inbound` package defines `inbound.Message{EnvelopeFrom, From,
  To []string, Subject, Text, HTML, Headers, Attachments int, SpamScore}` and `inbound.Parser`
  (`ParseWebhook(*http.Request) (*Message, error)`), with a parser per provider next to its sender. The
  first parser is Mailjet's (`sender/mailjet`), mapping `Sender`, `From`, `Recipient`, `Subject`,
  `Headers`, `Text-part`, `Html-part`, the `AttachmentN` count and `SpamAssassinScore`.
- **In pcom**, `POST /hooks/mail-inbound` sits outside sessions and CSRF, with basic auth in the URL
  registered with Mailjet. The parser is chosen by `MAIL_INBOUND_PROVIDER`. The route answers 200 to any
  authorized request, so the provider doesn't retry a mail pcom drops on purpose, and 500 when the database
  fails. Mailjet doesn't document retries for Parse, so a reply that arrives during a database outage may
  be lost.
- **DNS**: `REPLY_ADDRESS` (empty turns the feature off) is on a subdomain such as `reply.pcom.example`,
  with its MX record pointing at `parse.mailjet.com.`. Mailjet requires the domain to be a verified sender
  domain. The main domain's mail is untouched. `docs/running.md` describes the setup.

### New mails

| Name | To | Content | Reply-To kind |
|---|---|---|---|
| `author_email_reply` | the author | "<address> replied to your post", the text, a link to the thread | `author_thread` |
| `subscriber_thread_answer` | the subscriber | the author's answer (markdown rendered for mail, as comment mails do), their last message quoted | `subscriber_thread` |
| `email_reply_not_posted` | an account user | why, and their text | none |

F11's `subscriber_new_post` and the existing comment mails gain their Reply-To and footer lines, so their
goldens change; `git diff --stat` shows exactly those.

### Effects on other waves

- **F11**: the post fan-out writes `subscriber_post` tokens. TG's `Headers` carries `Reply-To` and
  `Auto-Submitted`; if gogo's `sender.Mail` gets a `ReplyTo` field instead, that is used.
- **F12**: a complaint about `author_email_reply` comes from the author. It must not suppress the author's
  address; it turns off messages from that subscription (`email_subscriptions.replies_blocked_at`), which
  the controls list shows. A complaint about `subscriber_thread_answer` is a complaint about a subscriber
  mail, so F12's rule (delete that address's subscriptions) applies.

### Provider facts (TV)

Read from Mailjet's pages on 2026-11-05. "Not documented" means the pages say nothing on the point.

| Point | Mailjet Parse API |
|---|---|
| Own subdomain | MX on the domain or subdomain to `parse.mailjet.com.`; the domain must be a verified sender domain |
| Addresses | A parse route maps one address (`Email`); other local parts and `+` tags are not documented, so pcom uses one fixed address |
| Webhook fields | `Sender`, `Recipient`, `Date`, `From`, `Subject`, `Headers`, `Parts`, `Text-part`, `Html-part`, `AttachmentN`, `SpamAssassinScore`, `CustomID`, `Payload` |
| Authentication results | None: no dedicated field, and `Headers` carries only the message's own headers. The raw message is not posted |
| Webhook auth | HTTP basic auth in the URL, HTTPS recommended |
| Size limit | Not documented |
| Retries | Not documented for Parse |
| Plan | "available only for users on paid Mailjet plans (Premium 50k and above)" |
| Sources | [basic setup](https://dev.mailjet.com/docs/email-api/parse-api/basic-setup), [webhook payload](https://dev.mailjet.com/docs/email-api/parse-api/delivered-to-webhook), [own domain](https://dev.mailjet.com/docs/email-api/parse-api/use-own-domain), [attachments](https://dev.mailjet.com/docs/email-api/parse-api/manage-attachments), [parseroute API](https://dev.mailjet.com/openapi/openapi-mailjet/parse/post_v3_parseroute) |
