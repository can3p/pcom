## F15 — Notes: private snippets, typed or spoken, that feed posts

Status: running · Depends on: an STT provider key for production only · Branch: `feat/f15-notes`

An author jots down small pieces of information as they come (typed, or spoken into the phone) and later
builds a post from them. Notes are private to their author, editable, tagged, and reachable from the post
editor, where a note can be inserted at the cursor or appended to the post as it is. A spoken note keeps its
recording; its text comes from a speech-to-text (STT) provider, made once per recording and as cheaply as the
provider allows.

The plan below is drafted against the recommended answer of each open question; a different answer changes
the tasks it names.

Decided on 2026-11-05:

- **iPhone first, Android right after (Q-N8).** The iOS path (the notes API with a scoped key, called by a
  Shortcut) comes before the Android one (installed web app, share target); both are in this wave.
- **API keys get scopes (Q-N12).** A user can hold several keys, each named and scoped; the key in a phone
  Shortcut can only create and read notes.
- **Android dictation works through the web page with the screen on (Q-N13).** Pocket dictation (a native
  wrapper) is a later wave if it proves needed.
- **No location is stored (Q-N9).**
- **Quotes from books are a main use of photos and shares.** Kindle (iOS and Android) and paper books, with
  as little retyping and as few movements as each platform allows.
- **No server-side text recognition (Q-N14).** Both phones recognize text on the device for free.
- **No Kindle notebook import (Q-N15).** Quotes come in one at a time, by sharing.
- **API keys are stored hashed (Q-N16)** and shown once, at creation; the existing key keeps working until it
  is replaced.
- **Notes get attached to posts in the next wave, F16** (`docs/plan/f16.md`). This wave's link table is
  shaped for it, so F16 needs no change to it.
- **Groq through the OpenAI-compatible backend (Q-N1).**
- **Deleting a note is final, with no trash (Q-N18).**
- **Note photos are public by URL, like a draft's images (Q-N17).** They are `media_uploads` images served by
  `user-media/:fname/:class` and the CDN, so a note's photo is inserted into a post as it is.
- **Transcription is a job on the queue (Q-N6)**, now that `pkg/jobs` exists; nothing runs in a bare goroutine.
- **Tags live in columns, not only in the text (Q-N2)**, so they can be filtered, attached to a post (F16),
  renamed and set by actions; `#word` in the text is one way to set them (below).
- **The transcript is the note's text (Q-N3).** Editing it is editing the note; no copy is kept aside.
- **Inserting a note into a post marks it used, with an "unused" filter (Q-N4).**
- **Existing audio files are accepted (Q-N5).**
- **The language is detected, never preset (Q-N7)**; a note can be transcribed again in a chosen language.
- **No AI help on notes in this wave (Q-N10).**
- **10 minutes per recording, 60 minutes of transcription per user a day (Q-N11).**
- **Tags group notes without bookkeeping.** Most grouping happens without the author doing anything; what
  remains takes one tap or a word said while dictating.

### What a note is

- **Owned by one user, seen by nobody else.** No visibility setting, no sharing, no feed, no RSS, no
  comments, no mail; every read and write checks `note.user_id = actor.ID`, and a note of somebody else is a
  404, never a 403. The rows go with the user row (`on delete cascade`); pcom has no account deletion by the
  user today (#278), and an unconfirmed account that gets pruned has no notes.
- **A deleted recording is deleted from storage.** `media.MediaStorage` has no delete today (images stay in
  the bucket forever, also after their post is deleted). Recordings are personal data, so this wave adds
  `DeleteFile` to it (the S3 storage and tommy), and deleting a note, or replacing its recording, enqueues a
  `notes.delete_audio` job in the same transaction; the object goes when the job runs, since the bucket is not
  part of the transaction. Images keep today's behavior (Q-N17).
- **A body in markdown**, written with the same editor as a post: the `mdeditor` controller, the toolbar
  without the post-only commands (`Post` false in `partial--editor-toolbar.html`), image upload through the
  existing `upload_media` action. The body renders with `pkg/markdown` in the same view type as a post body,
  so what is appended to a post looks the same there. Capped by `NOTE_BODY_MAX_LENGTH` (default 20000, the
  post body's default).
- **Tags**: free-form, per user, lowercased and trimmed, in two `text[]` columns: `tags`, set by actions
  (a chip, bulk tagging, the focus, a suggestion, the API), and `text_tags`, derived from the `#word`s in the
  body on every save. A note's tags are their union; every filter, F16's tag attachment and the tag list
  read `tags || text_tags`, behind one GIN index on that expression. A tag from an action is removed with
  its chip; a tag from the text is removed by editing the text (its chip says so). Renaming or merging a
  tag rewrites both columns and the `#word`s in the bodies. Capped by `NOTE_TAG_MAX_LENGTH` (default
  40) and `NOTE_TAGS_MAX` per note (default 10). How they get there without bookkeeping is "Grouping
  without bookkeeping" below.
- **Optionally a source**: the book (or article) a quote comes from, with a locator (page, Kindle
  location). Sources are per user and are created by the captures themselves (below).
- **Optionally a recording** (below) and its transcription state.
- **Optionally used in posts** (Q-N4): inserting a note into a post records the pair in `note_post_links`, so
  the notes list can show "used in …" and filter unused notes. A note is never changed or deleted by being
  used.

### Voice notes and economical STT

- **Recording in the browser**, with `MediaRecorder`: mono Opus in WebM (Chrome, Firefox, Android) or AAC in
  MP4 (Safari, iOS), at a low bitrate (`audioBitsPerSecond` from `NOTE_AUDIO_BITRATE`, default 24000, handed to the
  controller as a value; the browser picks the closest it supports). An hour is ~11 MB, so a memo is
  far under every provider's upload limit and the server never transcodes: no ffmpeg in the image. Both
  containers are accepted as they are by every provider considered.
- **Upload of an existing audio file** (a phone's voice memo) goes through the same endpoint (Q-N5).
- **Limits**: `NOTE_AUDIO_MAX_DURATION` (default 10m, checked in the browser and on the server from the
  container's duration header when present, else by size), `NOTE_AUDIO_MAX_BYTES` (default 8 MiB: ten
  minutes is ~2 MB at the page's bitrate and ~5 MB from the iOS Shortcut's AAC). Every request body is
  already capped by `bodyLimits` in `pkg/web/app/limits.go` (1 MiB except the routes it names), so the
  notes routes that take files (`/controls/action/note_audio`, `/controls/notes/share`, `POST /api/v1/notes`) are added
  there with `NOTE_CAPTURE_MAX_BYTES` (default 32 MiB: one recording and a few photos), while each file is
  checked against its own cap (`NOTE_AUDIO_MAX_BYTES`, `MAX_UPLOAD_SIZE` for an image) in the service. The
  server's `ReadTimeout` (60s) bounds a slow upload; the page's scaled photos and low-bitrate audio keep a
  capture far under it on a mobile connection, and T7 checks one on a throttled network. Per user
  `STT_MINUTES_PER_DAY` (default 60) and a site-wide `STT_SITE_MINUTES_PER_DAY` (default 0, no cap), counted
  from `stt_requests` rows with `status = 'ok'`, as proofreading counts its requests.
- **Storage**: the recording is a `media_uploads` row with `kind = 'note_audio'` (new column, default
  `'image'`) in the same bucket, under an `audio/` prefix. It is **not** served by `user-media/:fname/:class`
  or the CDN: that route is public by file name and does image processing. A new route
  `GET /controls/notes/:id/audio` checks ownership and streams the object with `Range` support (an `<audio>` element
  seeks with ranges), `Cache-Control: private`.
- **Transcription is made once per recording, never on edit**, and becomes the note's text, which the
  author edits like any note. Nothing else is kept: the recording is the original.
- **A job on the queue, with a state on the note.** The upload saves the note (`transcription_status`
  `pending`; the enum is `none | pending | done | failed`) and the recording, and enqueues a
  `notes.transcribe` job (`pkg/jobs`, River) in the same transaction, so a transcription exists exactly when
  its note does. The job's args are the note id and the upload id; the worker re-checks both at run time (the
  note may be deleted, or its recording replaced, before the job runs; then it does nothing), calls the
  backend with `STT_TIMEOUT` (default 2m), and writes the text, `done` and the `stt_requests` row in one
  transaction. River's retries and backoff replace any hand-written retry loop above the backend's own;
  on the last attempt the worker sets `failed`, so the note shows "Transcription failed — try again" instead
  of waiting forever. The job is unique per note and upload, so a double tap or a retried upload transcribes
  once. Transcriptions run on their own River queue `stt` with `STT_WORKERS` (default 2) workers, so a slow
  provider never holds up mail; `pkg/jobs` gets named queues for that (T0). The page polls the note's state
  with htmx (`hx-trigger="every 3s"` while pending).
- **Language is detected, never set in advance.** Whisper's `language` parameter forces the language, not
  hints it: with English set, Russian speech comes back translated into English or as nonsense, so a
  per-user setting would break every memo in another language. Detection is reliable from a few seconds of
  speech and can miss on a very short or mixed-language memo; for that a note has "Transcribe again as…"
  with a language picker, which sends the recording once more with `language` set, counts against the
  limits, and replaces the text after a confirmation if the author has edited it.
- **What is sent and kept**: only the recording goes to the provider, only when the author made one. The
  privacy policy and the editor say so next to the record button, as the proofreading disclosure does.

#### Choosing the provider

Pluggable like F7's translation backends: `pkg/stt` with one `Backend` interface
(`Name()`, `Transcribe(ctx, Audio{Bytes, ContentType, Language}) (Result{Text, Language, Seconds}, error)`),
the shared layer doing retries on 429/5xx with `Retry-After`, the request row and the limits; a backend file
holds only the HTTP call. `STT_PROVIDER` picks one; empty turns voice notes off (no record button), typed
notes still work.

| Option | Price per hour of audio (2026, to be verified in T0) | Notes |
|---|---|---|
| **Groq, `whisper-large-v3-turbo`** (recommended first backend) | ~$0.04 (10 s minimum per request) | OpenAI-compatible `/audio/transcriptions`, multilingual Whisper quality, fast; a free tier with daily limits |
| OpenAI `gpt-4o-mini-transcribe` | ~$0.18 | same wire format as Groq, so a second backend is a few lines |
| Deepgram Nova-3 (pre-recorded) | ~$0.26 | good accuracy; own API |
| Self-hosted whisper.cpp on the app machine | no per-minute cost | needs CPU and RAM the fly machine doesn't have; small models are weak outside English; not worth it at a few hours a month |
| Browser Web Speech API | free | Chrome sends audio to Google, Firefox has none, no result for an uploaded file, can't be redone later: not a fit for "keep the recording, transcribe it" |

At ~$0.04 an hour, a heavy user recording an hour a day costs about $1.20 a month; the daily minute limits
bound the worst case. Since Groq and OpenAI share the wire format, the first backend is written as
"OpenAI-compatible" with the endpoint and model as settings
(`STT_OPENAI_COMPAT_ENDPOINT`, `STT_OPENAI_COMPAT_MODEL`, `STT_OPENAI_COMPAT_KEY`), defaulting to Groq's
endpoint and model. Tests use the existing WireMock harness (`pkg/testutil/wiremock`, `e2e.WithWireMock`),
under the path prefix `/stt`.

**Works locally, offline** (`docs/architecture.md`). `docker compose` gets a `wiremock` service that serves the
same mapping files the tests use (`pkg/stt/openaicompat/testdata/wiremock/`), and the app in compose points
`STT_OPENAI_COMPAT_ENDPOINT` at it with a dummy key, so recording a note on a laptop gives a canned
transcript ("This is a local transcript of 12 seconds of audio. #local") without an account or a network.
`localhost` is a secure context, so the microphone, the camera input and the service worker work there too;
a phone on the same network needs HTTPS, which the guide's notes-on-a-phone page explains for development.

### Pages

Every notes page and action is under `/controls`, as drafts and settings are: the group requires a login,
its actions and forms check CSRF, and the upload routes join `bodyLimits`' list of paths that take files.
F14's per-client rate limits don't apply to logged-in users or API keys, so nothing here needs a limit
class; the STT minutes are the limit that matters.

- **`/controls/notes`** (a header menu entry "Notes" for logged-in users): a quick-capture box at the top (a textarea
  that saves on Ctrl+Enter, a record button), the tag bar (below), then the list, newest first, paged by
  cursor with `PAGE_SIZE` like other lists, filtered by tags, by "unused" and by a text search over the body
  (`ILIKE`; full text search is not needed at this size).
- **The tag bar** filters tags out as easily as in. It shows the author's tags as chips with their counts,
  most used first, with a search box when there are many. A tap cycles a chip through include (the notes
  must have it), exclude (they must not) and off; the state is in the URL (`?tag=a&tag=b&not=c`), so a view
  can be bookmarked. A tag can also be **hidden**: "Hide" on a chip (or on the tag management screen) keeps
  its notes out of the list by default, for tags like `done` or a finished project, with "Show hidden (n)"
  bringing them back for one view. Hidden tags are per user (`note_tag_prefs (user_id, tag, hidden)`), and
  the tag bar and the post editor's Notes panel share one partial, so both filter the same way. Each item shows its rendered
  body (cut like a post in the feed), its tags, an audio player when it has a recording, the
  transcription state, and Edit / Delete.
- **`/controls/notes/:id/edit`**: the editor; saves in place like the post form (`hx-trigger` on change, "Saved"
  next to the button), Delete is red and asks first.
- **A Notes section on the Controls page** (`controls.html`, next to Drafts): the Inbox count, the five
  newest notes and links to all notes and to capture. The full list stays its own page, because it needs
  the tag bar and paging.
- Capture itself is on its own page, `/controls/notes/new` (below); `/controls/notes` is for reading and sorting.

### Deleting notes

A note is deleted by its author only, from wherever they meet it, and the delete is final once confirmed:
there is no trash, as there is none for posts.

- **Where.** Delete on each item of the list, on the edit page, for a selection ("Delete 5 notes", next to
  "Tag" in multi-select; a stack can be selected as a whole), and on the capture page's card of the last
  capture, so a recording made by mistake on the go is gone in two taps. The F16 post page offers Detach,
  not Delete, so removing a note from a post is never mistaken for deleting it.
- **Asks first.** The button is red and confirms, as every destructive action in pcom does; the
  confirmation says what goes: "Delete this note, its recording and 2 photos? This can't be undone." A note
  that was inserted into posts says that the text in those posts stays; F16 adds the posts it is attached to.
  A selection says how many notes and recordings.
- **What goes**, in one transaction: the note, its `note_images` and `note_post_links` rows, and a
  `notes.delete_audio` job for its recording; the object leaves the bucket when the job runs. The photos'
  files stay, like every image today (Q-N17, #278). `stt_requests` rows keep counting against the limits
  (their `note_id` becomes null), so deleting and recording again doesn't reset the daily minutes.
- **What stays**: text already inserted into a post (it is the post's text now); a source with no notes left
  (it is hidden from lists and picked again by the next quote from that book); a hidden-tag preference.
  A tag no note carries any more disappears from the tag bar by itself, since tags are read from the notes.
- **Mid-flight.** A transcription job whose note was deleted does nothing. A capture still waiting in the
  phone's upload queue is deleted there, never reaching the server. A delete of a note that is already gone
  (two tabs, a double tap) is reported as done, not as an error.
- **Not through the API.** The notes-scoped key creates and reads; a key stored in a phone Shortcut can't
  delete anything.

### Capture on the go

The case that matters most is the author walking, phone in one hand, wanting a thought or a photo stored in
as few movements as possible. Recording and uploading must never cost a lost note, and nothing is asked at
capture time that can be decided later.

**Rules every capture path follows**

- **Stop is save.** No "Save" button, no form to confirm, no tag prompt: stopping a recording or taking a
  photo creates the note. Tags, text and cleanup happen later, on `/controls/notes`, where untagged notes form the
  "Inbox" filter.
- **Nothing is lost on a bad network.** The recording or photo is written to IndexedDB first, then uploaded
  with retries by the service worker; the capture page shows "Saved on the phone, uploading…" and then
  "Saved". A note created offline keeps its capture time (`notes.captured_at`, sent by the client) so the
  list order is when it was said, not when it arrived.
- **The screen stays on while recording** (`navigator.wakeLock`), because a page's recording stops when the
  screen locks or the browser goes to the background, on iOS always. Dictating with the phone in the
  pocket is what the native paths below are for.
- **Photos are first-class.** A photo note is one or more images and optional text or voice. The camera
  opens straight from the page with `<input type="file" accept="image/*" capture="environment">`; the
  client scales the photo down to `NOTE_PHOTO_MAX_DIMENSION` (default 2048 px) as JPEG before upload, which
  saves mobile data, stays under the upload limit and turns any HEIC into JPEG. The server keeps
  accepting only PNG, JPEG and WebP; HEIC sent by a native shortcut is converted by libvips if its build has
  libheif, otherwise refused with a message to add "Convert to JPEG" in the shortcut (T0 checks the build).
  "Photo + dictate" records a voice caption into the same note.

**Paths, cheapest first**

| Path | Platform | Movements to start capturing | Works with the screen locked |
|---|---|---|---|
| Native shortcut calling the notes API (Shortcuts "Record Audio" or "Take Photo", then "Get Contents of URL"), bound to the Action button, Back Tap, a lock-screen or Control Center control, or Siri | iOS | 1 (press the Action button) | recording yes; the upload may ask to unlock (T0 checks) |
| Share a voice memo, photo or text from another app to pcom (`share_target` in the manifest) | Android (installed PWA) | the share sheet, 2 taps | n/a |
| App shortcut on the installed PWA icon (`shortcuts` in the manifest: "Dictate", "Photo") | Android | long-press the icon, 1 tap | no |
| Installed PWA, `start_url` = `/controls/notes/new`, three big buttons: Dictate, Photo, Type | both | open the app, 1 tap | no |
| `/controls/notes/new` in the browser | both | as above, plus finding the tab | no |

`/controls/notes/new?start=voice` and `?start=photo` start that mode as the page opens. Whether the browser grants the
microphone without a tap on the page differs (Chrome keeps the grant per site; iOS Safari asks again in some
cases), so the page falls back to one big button; T5 records what each browser does.

**The capture page is light.** `/controls/notes/new` loads only its own controller and no list, and gets a budget in
`TestFirstVisitWeight`, so it opens fast on a weak connection. The 30-day sliding session (`pgsession`)
keeps a phone logged in; the installed PWA shares the browser's cookies on Android, but on iOS a home-screen
app has its own storage, so it logs in once by itself.

**The web app manifest** (`cmd/web/client/static/site.webmanifest`, today without a name or start URL) gets
`name`, `short_name`, `start_url`, `scope`, `shortcuts` and `share_target`
(`POST /controls/notes/share`, `multipart/form-data`, accepting `audio/*`, `image/*` and text). A share target
needs a service worker; pcom has none yet. It is registered only from the notes pages and caches only the
capture page's assets, so the rest of the site keeps working as it does now.

**The notes API** (`docs/api.md`) is what the native shortcuts call, so it is part of this wave:
`POST /api/v1/notes` (multipart: `text`, `tags`, `captured_at`, any number of `image` files and at most one
`audio` file) and `GET /api/v1/notes` (paged like posts), with the existing Bearer API keys. A key that lives
on a phone in a shortcut should be able to do less than a full key (Q-N12). The guide gets a page with a
ready-made iOS shortcut (an iCloud link to it, and the steps to build it by hand) and the Android setup.

### Quotes from books

A quote is a note with a source. The text is never retyped: it arrives as text from the phone's own reader
or its on-device text recognition, which is free, fast and works offline; pcom only parses and stores it.

| Where the quote is | iPhone | Android |
|---|---|---|
| Kindle app | select the passage → Share → the pcom Shortcut in the share sheet (it receives text and images) | select the passage → Share → pcom (the installed web app's share target) |
| Paper book | camera → Live Text → select the passage → Share → the pcom Shortcut; or "Quote from photo" in the Shortcut: Take Photo, then "Extract Text from Image" (on-device), sending the text and the photo | Google Lens or the camera's text selection → select → Share → pcom |

- **Parsing what is shared.** `pkg/notes/capture` turns shared text into a note: it recognizes Kindle's
  share formats (the quote, then the title, author, location or page and a link) and makes a quote with its
  source; a shared URL becomes a note with the link; anything else is plain text. The formats are pinned by
  golden tests over real samples the owner collects in T4 (a few shares from Kindle on each platform, a
  Live Text share), since Kindle doesn't document them. What doesn't parse is kept whole
  as a plain note, never dropped. Kindle may share an image card instead of text for some books; the
  Shortcut then runs "Extract Text from Image" on it, and the web page keeps the image as a photo note.
- **Sources need no setup.** A parsed quote finds or creates its source by normalized title and author, so
  every quote from one book lands in one group. A plain photo or note can be given a source with one tap
  from the recent ones (the book being read now is usually the first). Sources can be renamed and merged,
  for the rare share that spells a title differently.
- **A photo of a page stays with its text.** The photo is kept with the quote, so the author can check the
  recognized text against it; the text is editable like any note.
- **No server-side OCR.** Both phones recognize text on the device for free; a photo that came without text
  stays a photo note, and its text can be typed or dictated next to it.
- **In a post** a quote is inserted as a blockquote with an attribution line (`— Author, *Title*`, and the
  page when known); the attribution format is one template in `pkg/notes/capture`.

### Grouping without bookkeeping

The author shouldn't have to keep a taxonomy. Notes group themselves where pcom knows enough, and tagging by
hand is one word or one tap, never a form.

1. **Groups that need no tagging.** By source (every quote from a book), by post (notes used in it, Q-N4),
   and by capture session: notes captured within `NOTE_SESSION_GAP` (default 30m) of each other show as one
   stack in the list ("Tuesday evening, 7 notes"), computed in the query, not stored. A stack can be tagged
   or given a source as a whole.
2. **Focus.** The capture page, the Shortcut's notes and the share target all apply the author's current
   focus, a tag chosen with one tap from recent tags ("now writing: essay-on-walking"). It shows as a chip
   on the capture page and stays until changed or until `NOTE_FOCUS_IDLE` (default 12h) passes with no
   capture, so a forgotten focus doesn't tag next week's notes. This is what makes the one-press iPhone
   capture tagged without a prompt.
3. **Tags written or said in the text.** `#word` anywhere in a note's body is a tag, so there is no separate
   tag field to fill; editing the text edits the tags. In a transcript, "hashtag word" (and the forms
   Whisper writes it as, which T3 collects from real recordings) becomes `#word`. Saying "hashtag essay" at
   the end of a memo is the whole effort.
4. **Suggestions, free.** In the Inbox, each untagged note shows up to three of the author's existing tags
   whose words appear in its text or that other notes from its source or session carry; one tap applies
   one. No model call.
5. **Bulk and cleanup.** Select several notes (or a stack) and tag them at once; rename or merge a tag in
   one place, since free-form tags drift.

### In the post editor

- A **Notes** toolbar button (`partial--editor-toolbar.html`, `Post` true only) opens a side panel in
  `form--post.html` (the same column the proofread panel uses; both can't be open at once). The panel loads
  `/controls/notes/picker?tag=&q=` with htmx: a tag filter, a search box, and the notes as compact cards.
- The panel's filters include source and stack, so "all quotes from this book" is one tap.
- Each card has **Insert** (at the cursor), **Append** (to the end of the body, separated by a blank line)
  and **Open** (in a new tab). A quote is inserted with its attribution. Insert and Append put the note's markdown body as it is into the textarea via
  the `mdeditor` controller (a new `insertText(text, {atEnd})` method), then fire `postform:save` so the
  autosave records it; images in the note keep working since their URLs are the same media.
- On insert, the post's id (after its first autosave) and the note's id are posted to
  `note_mark_used`, which writes a `note_post_links` row with `how = 'inserted'` (Q-N4).
- The editor pages own this: `write.html`, `edit_post.html` around `form--post.html`, their page types in
  `pkg/web/pages_posts.go` (a `NotesEnabled` flag) and the routes that build them.

### Not in this wave

- Notes commands in the `blg` CLI (the API is in).
- A native app (also for pocket dictation on Android).
- Server-side text recognition of photos.
- Importing a Kindle notebook export.
- Attaching notes to a post and seeing them on the post page (F16).
- Tags on posts.
- Any AI help on notes: transcript cleanup, tag suggestions by a model, a draft from several notes.
