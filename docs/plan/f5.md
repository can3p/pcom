## F5 — Magic-link login, no passwords (planned, #175)

Passwords go. A user types their email; if it belongs to an active,
confirmed user, a one-time link is mailed; following it logs them in. There
is no password to reset, so the missing reset flow stops mattering.
Invitations stop asking for a password.

**Do not start before Q21–Q23 in `docs/open-questions.md` are answered.**
The defaults below are what the tasks build if the owner accepts them.

- **The link** is `/login/link/:token`: 32 random bytes, base64url, mailed
  once; only its SHA-256 is stored, in a new table `login_links (id uuid,
  user_id, token_hash unique, return_url, created_at, expires_at, used_at)`.
  It expires after 15 minutes, works once, and starting a session from it
  rotates the session (as password login does, #122).
- **Prefetching mail clients (Q21):** `GET /login/link/:token` changes
  nothing. It renders a page "Log in as <email>" with one button, a POST to
  `/form/login/link/:token` (CSRF as every `/form` route). Scanners fetch
  but don't submit forms. No JS auto-submit: scanners that run JS (Safe
  Links and the like) would log themselves in. The link isn't bound to the
  browser that asked for it, so asking on a laptop and clicking on a phone
  works.
- **No enumeration, no flood:** the login form always answers "If there is
  an account for that address, we've sent a link"; unknown, unconfirmed and
  rate-limited addresses send nothing. At most 3 unused links per user per
  15 minutes; more requests are silently dropped.
- **Return URL:** the login page's `return_url` (already validated today by
  `TestGuards_LoginReturnURL`) is stored with the link and followed after
  the POST.
- **Invitations (Q23):** the invite page asks for a username and a
  "Confirm sign up" button. That creates the user (email confirmed, the
  invitation proves the inbox) and mails a login link, as the issue says;
  the page says to check the mail. Open signup (`FORCE_SIGNUP` or registration
  open) works the same way: the confirmation mail's link is a login link
  that also confirms the address.
- **Passwords removed (Q22):** the password field of the login, invite and
  signup forms, the "Change Password" card and form, `ChangePassword`,
  `Authenticate`, the password hashing in `pkg/pgsession/hash.go`, the
  seed's and factory's passwords. The `users.pwdhash` column is dropped by
  a **separate later migration**, after a deploy has run without reading
  it, so a rollback still finds it.
- **Mail is now on the login path.** If Mailjet is down nobody can log in.
  The escape hatch is a CLI subcommand, `web admin login-link --email`,
  which prints a link for an operator (Q22 asks whether the owner wants it).
- **Tests log in without waiting for mail.** `e2e.Client.LoginAs(email)`
  issues a link through the accounts service and POSTs it, so the hundreds
  of logins in the suites don't each wait for the mail queue. The mail
  itself is asserted on tommy (as every E2E mail is) by the tests that own
  the flow.

### M0

Contract work: the coordinator does it, or a strong subagent. Owns a new
migration `migrations/<timestamp>-login_links.sql`, the regenerated
`pkg/model/core`, a new `pkg/repo/login_links.go`, a new
`pkg/service/accounts/links.go` and `links_test.go`, a new
`pkg/mail/login_link.go` (with a golden in `pkg/mail/testdata` and a row in
`mail_test.go`), `pkg/service/accounts/accounts.go` (constructor only),
`e2e/client.go`, `e2e/harness.go`, `e2e/browser/browser.go` and every
caller of `LoginAs` (`e2e/smoke_test.go`, `e2e/seed_test.go`,
`e2e/guards_test.go`, `e2e/helpers_test.go`; the change at each call site
is mechanical).

- `accounts.RequestLoginLink(ctx, email, returnURL) error` (silent for an
  unknown, unconfirmed or rate-limited address) and
  `accounts.LoginWithLink(ctx, token) (*core.User, returnURL string, err)`
  (`ErrNotFound` for an unknown, used or expired token; marks it used in
  the same transaction). `accounts.IssueLoginLink(ctx, user) (token string,
  err)` is the shared step, used by the CLI and the test harness.
- Table test: request for a confirmed user mails one link (asserted on the
  queued mail); unknown, unconfirmed and over-the-limit addresses mail
  nothing; a link logs in once; a used, expired or garbage token fails;
  the address is compared lowercased (as login is today).
- The harness: `LoginAs(email)` issues a link and POSTs the confirm form;
  the browser `login` helper copies that session as today. Password login
  still works after M0, so the tree stays runnable.

### M1

Owns `pkg/forms/form_login.go` and its test, `pkg/auth/auth.go`,
`pkg/web/app/routes_auth.go` (the login and link routes),
`cmd/web/client/html/login.html`, `cmd/web/client/html/form--login.html`,
a new `cmd/web/client/html/login_link.html`, `pkg/links/link.go`,
`pkg/links/link_test.go`, `e2e/guards_test.go` (the route table and the
login tests: `TestGuards_LoginBadCredentials` becomes "no mail for an
unknown address", `TestGuards_LoginRotatesSession` and
`TestGuards_LoginReturnURL` go through the link), a new
`e2e/login_link_test.go` and `e2e/browser/accounts_test.go`.

- The login form has one field, email; on submit it shows the "check your
  mail" message whatever the address.
- `GET /login/link/:token` renders the confirm page without touching the
  token (an invalid token shows "This link has expired" and a link back to
  the login form); `POST /form/login/link/:token` logs in and redirects to
  the stored return URL or `/feed`.
- E2E (`login_link_test.go`): the link from the mail tommy received,
  fetched with GET twice, still works once with POST; a second POST fails.
- Browser test: a user asks for a link, opens it from tommy's mail, presses
  the button and lands on their feed.
