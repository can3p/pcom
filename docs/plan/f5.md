## F5 — Login with an emailed code, no passwords (planned, #175)

Passwords go. A user types their email on the login page; if it belongs to
an active, confirmed user, a one-time code is mailed; the same page then
asks for the code, and typing it in logs them in. There is no password to
reset, so the missing reset flow stops mattering. Invitations stop asking
for a password.

Decided on 2026-10-01 (`docs/open-questions.md`):

- **Q21. A typed code, not a link.** The mail carries a code and no link, so
  mail clients and link scanners that prefetch URLs can't log anybody in,
  and no interstitial page is needed. The code is typed into the login page
  where the email was entered; reading the mail on a phone and typing the
  code on a laptop works.
- **Q23. Invitations:** the invite page asks for a username and a "Confirm
  sign up" button; that creates the user (email confirmed: the invitation
  proves the inbox) and mails a code, and the page turns into the code entry,
  as the login page does. Open signup (`FORCE_SIGNUP` or registration open)
  works the same way: the confirmation mail carries a code, and entering it
  confirms the address and logs in.

**Do not start before Q22 is answered** (removing the password column and
the operator's way in).

### The flow

- **Step 1, `POST /form/login` with the email** starts a *login attempt*: a
  row in a new table `login_attempts (id uuid, user_id null, code_hash,
  return_url, created_at, expires_at, tries, used_at)`, whose id goes into
  the session. If the address belongs to an active, confirmed user, the
  code is mailed; otherwise the attempt has no user, nothing is sent, and
  the page looks exactly the same, so the form never reveals whether an
  account exists. The page now shows "We've sent a code to <email> if there
  is an account for it", a code field, and "Use a different email".
- **The code** is 6 digits, from `crypto/rand`, stored only as an HMAC-SHA256
  keyed with `SESSION_SALT`. It expires after 15 minutes, works once, and
  allows 5 wrong tries; after that the attempt is dead and the user starts
  again.
- **Step 2, `POST /form/login/code`** checks the code against the attempt in
  the session (not against the email typed again), counts the try, and on a
  match starts a session (rotated, as password login does, #122) and
  redirects to the attempt's return URL or `/feed`. A code from another
  browser's attempt is useless here.
- **Limits:** at most 3 codes mailed per user per 15 minutes; a further
  attempt for that address creates no code and sends nothing, and the page
  still looks the same. Per-IP limits are out of scope (bot protection is
  #123).
- **Return URL:** the login page's `return_url` (validated today by
  `TestGuards_LoginReturnURL`) is stored on the attempt.
- **Passwords removed (Q22):** the password fields of the login, invite and
  signup forms, the "Change Password" card and form, `ChangePassword`,
  `Authenticate`, the password hashing in `pkg/pgsession/hash.go`, the
  seed's and factory's passwords. The default for the column: the
  `users.pwdhash` column is dropped by a **separate later migration**,
  after a deploy has run without reading it, so a rollback still finds it.
- **Mail is now on the login path.** If Mailjet is down nobody can log in.
  The default escape hatch (Q22): a CLI subcommand, `web admin login-code
  --email`, that issues a fresh code for that user's newest open attempt
  and prints it, for an operator to pass on; the user has started the
  attempt on the login page as usual.
- **Tests log in without waiting for mail.** `e2e.Client.LoginAs(email)`
  posts the email, then gets the attempt's code through a test-only hook of
  the accounts service (`accounts.IssueLoginCode`, the step the CLI uses
  too) and posts it, so the hundreds of logins in the suites don't each
  wait for the mail queue. The tests that own the flow read the code from
  the mail tommy received, as every E2E mail is asserted.

### M0

Contract work: the coordinator does it, or a strong subagent. Owns a new
migration `migrations/<timestamp>-login_attempts.sql`, the regenerated
`pkg/model/core`, a new `pkg/repo/login_attempts.go`, a new
`pkg/service/accounts/codes.go` and `codes_test.go`, a new
`pkg/mail/login_code.go` (a golden in `pkg/mail/testdata` and a row in
`mail_test.go`; the mail has the code, how long it lasts, and a line saying
to ignore it if you didn't ask), `pkg/service/accounts/accounts.go`
(constructor only), `e2e/client.go`, `e2e/harness.go`,
`e2e/browser/browser.go` and every caller of `LoginAs` (`e2e/smoke_test.go`,
`e2e/seed_test.go`, `e2e/guards_test.go`, `e2e/helpers_test.go`; the change
at each call site is mechanical).

- `accounts.StartLogin(ctx, email, returnURL) (attemptID string, err)`:
  always returns an attempt; mails a code only for a confirmed user under
  the limit. `accounts.FinishLogin(ctx, attemptID, code) (*core.User,
  returnURL string, err)`: `service.Invalid("code", …)` for a wrong code
  (counted), `ErrNotFound` for a dead, used, expired or userless attempt.
  `accounts.IssueLoginCode(ctx, attemptID) (code string, err)` replaces the
  attempt's code and returns it, for the CLI and the harness.
- Table test: a confirmed user's attempt mails one code (asserted on the
  queued mail) and the code logs in once; unknown, unconfirmed and
  over-the-limit addresses mail nothing and their attempts never log in; a
  wrong code is counted and the sixth try fails even with the right code; an
  expired attempt fails; the address is compared lowercased (as login is
  today).
- The harness: `LoginAs(email)` as above; the browser `login` helper copies
  that session as today. Password login still works after M0, so the tree
  stays runnable.
