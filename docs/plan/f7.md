## F7 — Translating posts and RSS items to English (#144)

Status: planned · Depends on: an Azure Translator key · Branch: `feat/f7-translation`

A reader can translate a post or an RSS item into English, see the original
again at any time, and ask for every post in a given language to be
translated for them ("I don't read German"). The markdown structure stays
intact; only the text is translated. Translations are cached and shared
between readers, refreshed when a post is edited, never made for drafts,
and always shown as what they are: automatic translations.

Decided on 2026-10-01:

- **Q25. The author decides.** A post is translatable only if its author
  ticked "Allow readers to translate this post" in the editor: a new column
  `posts.allow_translation boolean not null default false`, so no existing
  post is sent anywhere until its author opts in. The checkbox says the text
  is sent to an external translation service. The API (`blg`) takes an
  optional `allow_translation`; leaving it out keeps the stored value
  (documented in `docs/api.md`). Turning it off deletes the post's cached
  translations and queued jobs. RSS items have no pcom author and are
  already public, so they are always translatable.
- **Q26. Pluggable backends, Azure Translator first.** Translation is common
  infrastructure with one interface and interchangeable backends, chosen by
  configuration. The first backend is Azure Translator (Text API v3.0; the
  F0 free tier covers 2M characters a month, S1 is $10 per million).
  More backends will be implemented (Anthropic, DeepL, Google, a
  self-hosted LibreTranslate), all compiled in; **the deployment chooses
  one** with `TRANSLATION_PROVIDER`. Adding a backend is a new package, its
  own config group and its stubs, with no change to the service, the cache
  or the UI.
- **Configuration is scoped to the provider.** Nothing is global: every
  setting lives under `translation-…`/`TRANSLATION_…`, and each backend's
  settings under its own namespace inside it (`TRANSLATION_AZURE_KEY`, later
  `TRANSLATION_DEEPL_KEY`). Only the selected backend's settings are
  required, checked at startup.
- **Tests run against WireMock with JSON stubs** (below), not tommy: tommy
  stands in for the systems pcom sends to and stores in (mail, S3), while
  third-party APIs pcom calls for an answer are stubbed. No test calls a
  real provider.

Q27 (language detection) is deferred to T0, which picks a local Go
library, checks its license and binary size, and records the choice in
this file; `wave-close` carries it into the docs.

### The translation infrastructure (`pkg/translate`)

- `translate.Backend` is the one interface a provider implements:
  `Name() string` (stored with each translation), `DisplayName() string`
  (shown to readers: "Azure Translator"), `Limits() Limits` (most segments
  and characters per request) and `Translate(ctx, Request) ([]string,
  error)`, where `Request{From, To string; Segments []string}` and every
  segment is a small HTML fragment (below). A backend returns exactly one
  translation per segment, in order, or an error.
- **Shared, not per backend:** splitting a request into chunks under the
  backend's `Limits`, retrying 429 and 5xx with backoff (honouring
  `Retry-After`), counting characters, and checking the result's shape (the
  same number of segments, the same protected spans; a mismatch is an error,
  never a partial translation). A backend file holds only the HTTP call and
  the mapping to and from its wire format.
- **Registry:** `translate.New(cfg)` returns the backend named by
  `TRANSLATION_PROVIDER` (a `choice` of the compiled-in backends, `azure`
  for now; empty turns the feature off: no controls, no settings card, no
  editor checkbox).
- **Configuration**, in `pkg/config` (`NamespaceDelimiter` is `-`, the env
  one `_`, as for `USER_MEDIA_*`): a `Translation` group with
  `namespace:"translation" env-namespace:"TRANSLATION"` holding `provider`,
  the two limits below, and one nested group per backend. Azure's is
  `namespace:"azure" env-namespace:"AZURE"`: `TRANSLATION_AZURE_KEY` (a
  `settings.Secret`), `TRANSLATION_AZURE_REGION` and
  `TRANSLATION_AZURE_ENDPOINT` (default
  `https://api.cognitive.microsofttranslator.com`, pointed at WireMock in
  tests). go-flags `required` can't depend on the provider, so
  `Config.Validate` requires the selected backend's settings and ignores
  the others'. `pkg/config`'s table test gets a row per setting.
- **Azure backend:** `POST {endpoint}/translate?api-version=3.0&from=..&to=en&textType=html`
  with headers `Ocp-Apim-Subscription-Key` and
  `Ocp-Apim-Subscription-Region`, a body of `[{"Text": segment}, …]` (at
  most 1,000 elements and 50,000 characters a request), spans that must
  stay as they are marked `class="notranslate"`. T0 checks these against
  Microsoft's current documentation before writing the client.
- **Switching providers** keeps the cache: each translation records the
  backend that made it, and the label says so. A row is re-made only when
  its source changes.

### Structure

The text is sent block by block, never as a document, and never as words
torn out of their sentence. `pkg/markdown` walks the goldmark AST and turns
each translatable block (a paragraph, heading, list item, table cell, image
alt, the subject) into one segment: its inline content as minimal HTML
(`<em>`, `<strong>`, `<a data-i="3">`), with code spans, URLs, `@handles`
and anything else that must not change as
`<span class="notranslate" data-i="n">`. Code blocks, block tags
(galleries), embedded videos and raw HTML are not sent. Translated
segments are parsed back and put in place of their blocks, links and
protected spans restored by `data-i`, so the result is markdown again and
renders through the usual renderer. RSS items are sanitized HTML: their
block elements become segments the same way, with
`golang.org/x/net/html`.

### Readers see that it is automatic

- Every translated text carries a visible line above it: "Automatically
  translated from German by Azure Translator · Show original" (the
  language from the detection, the name from `DisplayName`). There is no way
  to show a translation without it.
- The translated block has `lang="en"`, the original its detected language.
- The settings card says translations are made by a machine and may contain
  mistakes; the user guide and the privacy policy say the same, and the
  privacy policy names the provider.

### The rest of the behavior

- **Who can trigger a translation:** a logged in user, for a published
  post that allows translation or an RSS item they can read now (the
  reading service's rules). Anonymous visitors see no control and the route
  refuses them, so outsiders can't spend the budget. Drafts and edit
  previews are never translated.
- **Budget, in characters** (what MT providers bill): a per-user daily limit
  (`TRANSLATION_USER_DAILY_CHARS`, default 50,000, about eight posts) and
  a site-wide monthly limit (`TRANSLATION_SITE_MONTHLY_CHARS`, default
  2,000,000, Azure F0's cap). Cache hits are free and not counted. Over a
  limit, the reader sees "Translation is not available right now" and the
  original.
- **Language detection** is local and free (Q27): a Go library, run when a
  post is published or edited and when an RSS item is imported, stored in a
  `language` column (ISO 639-1, null when unsure). Content already in
  English, or of no detected language, gets no control.
- **Cache:** a table `translations (source_kind post|rss_item, source_id,
  target_lang, source_hash, provider, subject, body, chars, created_at)`,
  unique on `(source_kind, source_id, target_lang)`. `source_hash` is the
  SHA-256 of the source subject and body; a row whose hash no longer
  matches is stale and not shown. Deleting a post deletes its translations.
- **Edits:** saving a published post whose translations exist queues their
  re-translation (a job row picked up by a worker, as mail is sent), so the
  author never waits on the provider; until then readers see the original
  and "Translation is being updated". Background re-translations count
  against the site-wide limit only.
- **Preferences:** a settings card "Translation" with the languages to
  always translate (a multi-select of the detected languages; English is the
  only target for now, stored per user so another target is a later change).
  For those languages, posts and RSS items load translated, with "Show
  original" one click away; otherwise a "Translate" button loads the
  translation in place (htmx).
- **Scope:** posts (feed, single post, journal, explore) and RSS items in
  the feed. Not comments, not profiles, not RSS outputs.

### Stubbing third-party APIs: WireMock

Chosen on 2026-10-01 over writing a stub server. Compared:

| Option | Stubs | Verifying calls | State |
|---|---|---|---|
| **WireMock** (`wiremock/wiremock` image, Java) | JSON mapping files, the de facto format: URL, header, JSONPath and `equalToJson` body matching; templated responses; faults and stateful scenarios | the request journal, counts, near-miss reports for unmatched calls | the standard; the image and the Go client [`go-wiremock`](https://github.com/wiremock/go-wiremock) (MIT) are active in 2026 |
| Hoverfly (Go, Apache-2.0) | JSON simulations in its own, more verbose schema; templating | journal API | active; a capture-and-replay proxy first |
| Killgrave (Go, MIT) | JSON/YAML "imposters" | none | last push 2025-02 |
| Smocker (Go server, MIT) | YAML | history, session verification | last release 2025-03 |
| `jarcoal/httpmock`, `h2non/gock` | Go code | in-process only | can't reach the app: the E2E harness runs it as a separate process |

WireMock is the one with plain JSON stubs and call verification, and pcom
already runs test containers through testcontainers-go
(`pkg/testutil/testdb`, `pkg/testutil/tommy`), so it fits as one more:

- **`pkg/testutil/wiremock`**, shaped like `pkg/testutil/tommy`: one
  shared container per test binary, a pinned image tag (the current 3.x
  release, chosen in TM), started with `testcontainers.Run`. Not the
  experimental `wiremock-testcontainers-go` module: plain testcontainers is
  already a dependency and enough.
- **Stubs are JSON files next to the backend they serve**:
  `pkg/translate/azure/testdata/wiremock/mappings/*.json` (and `__files/`
  for long bodies). The helper imports every registered mapping directory
  through the admin API at start. Each API is mounted under its own path
  prefix (`/azure-translator/translate`), so one container serves every
  third-party API, and the backend's endpoint setting is the container URL
  plus that prefix.
- **A stub is a canned exchange**: an `equalToJson` request body (the
  segments a test sends) and Azure's response to it, so the fixtures show
  exactly what pcom sends and receives. Tests use their own content, so
  parallel tests on the shared container don't collide, and verify their
  calls by matching that content. Headers are matched too
  (`Ocp-Apim-Subscription-Key` present); a catch-all stub at the lowest
  priority answers Azure's 401 body without them. A retry stub is a
  scenario: 429 with `Retry-After`, then 200.
- **An unmatched call fails the test**: the helper reads WireMock's
  unmatched requests at cleanup and reports the near misses.
- **Verifying** uses `go-wiremock` (a request pattern and a count), added to
  `go.mod` by TM; tests assert, for example, that a cache hit made no call.
- **E2E and browser tests** get it through a harness option,
  `e2e.WithWireMock()`, which starts the shared container and sets
  `TRANSLATION_PROVIDER=azure` and `TRANSLATION_AZURE_ENDPOINT`.
- A later backend adds its mapping directory and prefix; nothing else
  changes.

### T2
