## R7 — Structured logging with zap

Status: planned · Depends on: — · Branch: `refactor/r7-logging`

Replace the three ways the code logs today with one
[zap](https://github.com/uber-go/zap) `*zap.Logger`. Counted on 2026-10-10,
outside tests and generated code: 19 calls to the standard `log` package, 29
to `log/slog` (including the level plumbing in `pkg/config` and
`cmd/web/serve.go`), and 12 `fmt.Print*` calls, of which those in
`cmd/web/cmd_debug.go`, `cmd/web/cmd_admin.go`, `cmd/web/main.go` and
`website/` are a CLI's output to its user and stay.

gogo v0.2.0 already logs through zap: `forms.DefaultHandler(c, logger, form)`
takes the logger (v0.1.0 logged a failed save through `slog`),
`testcontainers/postgres` takes an optional `WithLogger` (it defaults to a
no-op logger), `settings.Secret` dropped its `slog` `LogValue` (it still
redacts through `String()`, so `zap.Stringer` shows it redacted), and
`sender/console.NewSender` and `util/logging.LogValue` take a logger (pcom
uses neither). L0 bumps gogo, so after it nothing in pcom's build logs
through `slog`.

F7's translation worker (`pkg/service/translations`, on
`feat/f7-translation`) logs too: whichever of F7 and R7 merges second
converts it.

Rules for the converted code:

- The logger is passed explicitly: to constructors of long-running workers
  (mail sender, feed poller, login pruner, media server), and through the
  request context for handlers and services. No `zap.ReplaceGlobals`, no
  package-level logger.
- Structured fields, not formatted strings:
  `logger.Error("send failed", zap.Error(err), zap.String("mail_id", id))`.
- An error is either returned or logged, never both. It is logged once, at
  the boundary that handles it (the request middleware, the worker loop). An
  error a service deliberately swallows (a notification that failed to queue)
  is handled there, and logged there.
- `fmt.Print*` remains only for a CLI subcommand's output to its user.

What L0 defines and the other tasks use:

- `pkg/logging`: `FromContext(ctx) *zap.Logger` and `WithLogger(ctx,
  logger)`. `FromContext` works on a `*gin.Context` as well as a plain
  `context.Context` (services receive either; gin's `ContextWithFallback` is
  off), and returns a no-op logger when none is set, so a service called
  from a test or a CLI subcommand never panics.
- Workers take the logger as an option, `WithLogger(*zap.Logger)`, like
  their other options (`dbsender.WithRetryIntervals`,
  `accounts.WithLoginLimits`, `server.WithPermaCache`), defaulting to a
  no-op logger. L1 and L2 don't edit `cmd/web/serve.go`: the coordinator
  passes the logger there after merging them.
- `pkg/testutil` has the observer helper; a test that asserts a log entry
  uses it rather than building its own core.
