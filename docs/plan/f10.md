## F10 — Styled HTML mails (#237)

Status: planned · Depends on: — · Branch: `feat/f10-mail-styling`

Every HTML mail pcom sends is a bare run of `<p>` tags: no layout, no colours, no fonts set
(`pkg/mail/templates/*.html`, 14 mails). After this wave every HTML mail has the same minimal look, in the
site's colours, built from one shared header and footer:

- **One layout.** A shared document (`templates/_layout.html`) with the header (the "pcom" wordmark linking to
  the site) and the footer (why the reader gets the mail, a link to the site). Each mail's own `<name>.html`
  holds only its content, the part between them.
- **The site's colours, system fonts.** The palette is the light theme of `cmd/web/client/scss/_tokens.scss`:
  ground `#faf6ee` around a surface `#fffdf8` card with a `#e7dfcf` line, text `#3a3526`, titles `#2b2719`,
  muted `#6e6754`, links and the button `#4f6328` with `#fff` on it. No web fonts: a system stack
  (`-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif`) and, for codes
  and `pre`, the `--font-mono` stack of the tokens.
- **Minimal.** One centred column at most 600px wide, generous spacing, a primary button for the mail's main
  action, a sunken box for quoted user content and for login codes. No images in the layout, no tracking.

Not in this wave: the text parts keep their content (only the footer line is shared, below), the subjects and
wordings stay, no unsubscribe or notification settings (there are none yet; `docs/guide/comments.md` says so).

### How it is built

**Two-phase rendering.** `Definition.Render` executes the mail's `<name>.html` with the input, as now, then
executes `_layout.html` with a `layoutData{Content template.HTML, Site links.Site}`. `Content` is the output
of `html/template`, already escaped, so wrapping it in `template.HTML` is safe; the package doc's rule ("a
markdown body … and nothing else is wrapped in template.HTML") gains this one exception, stated there. The
layout is parsed once at package init like the other templates; `declare` panics if it is missing.

**The site in every mail.** The header and footer link to the site root, so `Header` gains `Site
links.Site`, and every input's `Header()` fills it. Mails whose constructor has no site today
(`LoginCode`, `ConfirmSignup`, `AdminPageFailure`, `AdminSignupConfirmed`,
`AdminThrowAwayEmailSignupAttempt`, `AdminNewWaitingListMember`) take `site links.Site` as their first parameter,
like `Invitation`. Callers: `pkg/service/accounts/{codes,invites,signup}.go` (they have `s.ident.Site`) and
`pkg/web/app/router.go:66` (`siteOf(d)`); `grep -rn 'mail\.<Name>(' --include=*.go .` lists them all.

**CSS: one file, inlined at render.** Mail clients drop or ignore `<style>` unevenly (Gmail strips a whole
block on one error, and forwarding loses it), so the styles live in `templates/mail.css` (embedded) and are
inlined into `style` attributes when `Render` runs, by `github.com/vanng822/go-premailer/premailer` (MIT;
check its latest tag and that it keeps `@media` rules in a `<style>` block). Templates use classes
(`mail-button`, `mail-quote`, `mail-code`, `mail-muted`, …) and plain elements; element selectors (`p`, `a`,
`blockquote`, `pre`, `code`, `img`, `ul`, `table`) style the markdown bodies of posts and comments, which
carry no classes. The layout is table-based (`role="presentation"` tables, `width="600"` on the inner one,
`bgcolor` attributes as a fallback) so Outlook desktop centres it. Images in markdown get `max-width: 100%;
height: auto`.

**Colours stay the site's.** `TestMailCSS_MatchesTokens` (in `pkg/mail`) reads `mail.css` and
`cmd/web/client/scss/_tokens.scss` and checks that each colour the mail uses, named in a comment next to it
(`/* --accent */`), equals the light-theme token. It reads source by path on purpose; a move of either file
breaks it loudly.

**Dark mode, best effort.** `<meta name="color-scheme" content="light dark">` and an
`@media (prefers-color-scheme: dark)` block with the dark tokens, left in `<style>` by the inliner, for
clients that honour it (Apple Mail, iOS Mail). Others keep the light look or invert it themselves; nothing
else is attempted. The dark colours are checked against `_tokens.scss` by the same test.

**The text parts** gain the same footer: `Render` appends `templates/_footer.txt`, executed with the same
`layoutData`, after a blank line: `--` then `pcom · <site root>`. That is the shared footer of the
plain-text alternative; no `<name>.txt` changes.

**Goldens.** Every golden changes, since every HTML part now carries the layout. `UPDATE_GOLDEN=1 go test
./pkg/mail/...` rewrites them; check `git diff --stat` (the 31 files under `pkg/mail/testdata/`) and read two in
full. The goldens keep the full rendered mail: it is what is sent.

**Preview.** `/dev/mail/<sample>` already shows the HTML part in a sandboxed iframe; it needs no change,
and is how the owner looks at the result.

### M0

Contract work. Owns `pkg/mail/mail.go` (two-phase `Render`, the inliner, `declare` parsing the layout and the
text footer, `Header.Site`, the package doc's "Templates" section: the layout, the classes, the inlining, the
`template.HTML` exception), new `pkg/mail/templates/_layout.html`, `_footer.txt` and `mail.css`, every
`pkg/mail/<name>.go` for its `Header()` and, where it lacks one, the constructor's `site` parameter and the
sample's `Site: SampleSite`, the callers named above and their tests, `go.mod`/`go.sum` (the inliner), new `pkg/mail/css_test.go`
(`TestMailCSS_MatchesTokens`), and all of `pkg/mail/testdata/`. The `<name>.html` files stay as they are
in this task: the layout wraps the old content, so the diff of the goldens shows only the frame.

`mail.css` defines, for M1 and M2: the body and the card; `h1` (the mail's heading, `--title`, 22px, 800
weight falls back to bold); `p`, `a`, `ul`, `li`; `.mail-button` (an `<a>` in a `<p>`: `--accent` background,
`--on-accent` text, 8px radius, 12px 20px padding, block on narrow screens is not needed); `.mail-quote`
(a `--sunken` box with a 4px `--line` left rule, for quoted user content and markdown bodies, which renders
nested `p`, `pre`, `code`, `img`, `blockquote`, lists and tables readably); `.mail-code` (a login or
confirmation code: mono, 28px, letter-spaced, in a `--sunken` box); `.mail-muted` (`--muted`, 14px, for
fine print and the "Linked URL" lines); `pre` with `white-space: pre-wrap` (the page-failure report).

Tests (beside the goldens): every sample's HTML starts with `<!DOCTYPE html>`, contains the footer's site
link with `SampleSite`'s root, and has no `class=` attribute whose selector `mail.css` lacks a rule for
(inlining would silently drop it); the inliner keeps the dark `@media` block.

### M1

Owns the templates and goldens of the mails a user gets: `login_code`, `confirm_signup`,
`confirm_waiting_list`, `invite`, `new_post`, `post_comment_author`, `post_comment_participants`,
`post_prompt`, `post_prompt_answer` (`pkg/mail/templates/<name>.html`, their `testdata/*.golden`), and
`pkg/mail/new_post.go` for one new sample. Keep every sentence; change only the markup:

- a heading `h1` per mail (e.g. "New post from @alice", "Your login code"), taken from the subject's
  wording;
- the codes in `.mail-code`;
- the post and comment bodies and the prompt messages in `.mail-quote`;
- the mail's main link as a `.mail-button` ("Open the post", "Open the comment", "Accept the invitation",
  "Confirm your address", "Write the answer"), with the raw URL kept under it in `.mail-muted` for clients
  that drop styles; secondary links ("Linked URL") in `.mail-muted`.

A new sample `new_post_rich_body` (golden `testdata/new_post_rich_body.golden`, an empty file first) has a
body with a heading, a list, a code block, an inline image, a quote, a `{cut}` and a link, so the golden shows
markdown inside `.mail-quote` with every element styled.

### Decided with the owner

Settled on 2026-10-14:

- **Footer text:** "You get this mail because you have an account at pcom." plus the site link; for
  invitations and waiting-list confirmations, "You get this mail because somebody entered this address at
  pcom." No line about notification settings until they exist.
- **No preview text** (the hidden first line clients show in the inbox list): clients show "pcom" and then the
  heading. A per-mail `preheader` is a later change if the inbox line reads badly.
- **The inliner** (`go-premailer`) rather than hand-written `style` attributes, so markdown bodies get styles
  without a goldmark renderer per element.
