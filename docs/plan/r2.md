## R2 — go-flags configuration, single binary, compose-backed services (planned)

**Configuration rules:**

- Every setting is a `jessevdk/go-flags` option with paired `long:` and
  `env:` tags, declared once, so `--help` is the configuration reference.
- Required settings fail at startup and name the environment variable, never
  on the first request. An environment variable that exists but is empty
  counts as missing, which go-flags alone doesn't check.
- Credentials use a `Secret` type that doesn't print.
- There are no config files in a deployed environment, and no `if production`
  switches.

These helpers are gogo's since v0.1.0 (R3): parse with `settings.Parse`
instead of `ParseArgs`, and declare credentials as `settings.Secret`.

**Subcommands** are transports like the HTTP handlers: each calls a service
from RS and holds no queries of its own. `serve`, `seed`,
`admin invite --email --num`
(replaces `cmd/scripts/add_invite.go`), and
`admin registration --open/--close` (replaces
`cmd/scripts/toggle_open_registration`).

**Remove every scattered `os.Getenv`.** Today these are:

- `SESSION_SALT`, read in `auth.HashValue` on every call;
- `SENDER_ADDRESS`, at 13 call sites;
- `ADMIN_ADDRESS`, read into a package variable at init;
- `STATIC_CDN`, baked into the CSP string at init;
- `USER_MEDIA_*` and `SITE_ROOT`;
- `ENABLE_PPROF`;
- `FLY_APP_NAME`, which `util.InCluster()` uses as an `if production`
  switch.

Replace the switch with explicit settings, such as `--secure-cookies`,
`--hsts` and `--static-cdn`. This fixes #111 by construction.

**Mail goes through tommy; the console sender is dropped.**

- gogo v0.1.0 (R3) gives `sender/mailjet/config.Config` a `BaseURL`
  (`long:"api-base" env:"API_BASE"`): the host root, such as
  `http://localhost:8822`; gogo appends the `/v3` the SDK expects. Embed
  the config as a group with `namespace:"mj" env-namespace:"MJ"`.
- pcom always uses the Mailjet sender (still behind `dbsender`). Locally, the
  base URL points at tommy (`http://localhost:8822`, or `http://tommy:8822`
  in compose), with any credentials. The console sender and
  `--force-real-sender` are deleted.
- The email poll interval becomes a setting, so E2E tests don't wait 10
  seconds.
- The E2E harness starts a tommy test container (the same one that serves S3,
  below) and adds
  `app.Mails(t, filter)`, which polls `GET /api/v1/events?plugin=mail` until
  the expected mail arrives. **E2E and browser tests switch from the
  `outgoing_emails` queue to delivered mail**: they assert on what tommy
  received (recipient, subject, body), and flows that follow a link from an
  email (signup confirmation in `e2e/browser/accounts_test.go`) take it from
  the delivered message. The queue is an implementation detail that R4 may
  replace with a job queue, so after R2 no test under `e2e/` reads it
  (`git grep ListOutgoingEmails e2e/` is empty). Today that is
  `e2e/browser/accounts_test.go`, `comments_test.go`, `settings_test.go`,
  plus any W3 test added by then. `factory.ListOutgoingEmails` stays for
  package tests of `dbsender` itself.
- Unit and package tests keep using `fakesender`.

**Object storage everywhere; local file storage is dropped.**

- The S3 storage gets a path-style addressing option (`UsePathStyle`). tommy
  needs it, and today's client only does virtual-host addressing.
- Local development points at the compose `tommy` service's S3 listener
  (`http://localhost:9555`, or `http://tommy:9000` in compose; bucket
  `pcom-media`). W4 configures it to create the bucket at startup and to
  keep objects on a volume, so development uploads survive a restart.
- Delete `pkg/media/server/storage/local`, the `user_media` directory, and
  the `cmd/web/.gitignore` entries for it.
- **Tests use tommy as the S3 target** (`can3p/tommy:0.3.0` or later; Docker
  Hub tags have no `v` prefix. Its `s3` plugin listens on port 9000,
  path-style only). It is the same container that captures mail, so one
  container serves both. It accepts any credentials and unsigned requests.
  The container is started with `TOMMY_S3_BUCKETS=pcom-media`, so the bucket
  exists once the listener accepts connections and no create-bucket step or
  event is needed. Tests don't set `TOMMY_PERSIST`: each container starts
  empty. What was stored can be read back through
  `GET /api/v1/s3/buckets/{bucket}/objects[/{key}]` on the API port.
- **S3 storage tests** (`pkg/media/server/storage/s3`, against a tommy
  container started once per package):
  - upload, then download the same bytes and content type;
  - `ObjectExists` true and false;
  - a missing key maps to `media.ErrNotFound`;
  - the stored object's content type and size, read back through tommy's
    API.

  tommy accepts ACLs but doesn't enforce them. It does record the raw request
  headers on each `s3.object.put` event, so `ACL: private` is asserted as
  `X-Amz-Acl: private` through `GET /api/v1/events?plugin=s3`. Verified on
  2026-09-24 against `can3p/tommy:0.2.0` with pcom's SDK versions:
  create-bucket, a put with a private ACL, get, and `NoSuchKey` for a
  missing key all work with path-style addressing. The SDK sends a plain
  body (a `[]byte` reader over HTTP), not the `aws-chunked` encoding that
  tommy rejects.
- **The E2E harness** starts the tommy container (mail and S3, with the
  bucket configured), and passes the endpoint, bucket and path-style settings to the
  binary. It adds `app.S3Objects(t)`. The upload tests (W6.B5's upload
  through the settings page, W3.E4's `PUT /api/v1/image`) gain assertions that the object
  landed in the bucket with the right content type. They also check that
  requesting a resized class stores the cached variant (the caching media
  server writes it back to storage). The "upload, then GET the returned
  `/user-media` URL" assertions that W3 and W6 already made pass unchanged; they
  prove the switch from local files to S3 kept serving intact.
- Unit tests keep using `fakestorage`.

**Migrations at deploy:** the production image carries the `sql-migrate`
binary (built in the Dockerfile at `tools/Dockerfile`'s pinned
`SQL_MIGRATE_VERSION`), `dbconfig.yml` and `migrations/`, and fly's
`release_command` runs `sql-migrate up -env=production` in it (D2). There is
no `migrate` subcommand. `make migrate-prod` from W4 becomes a fallback, not the
deploy path.

Defaults of the new booleans are production-safe (D1): `SECURE_COOKIES`,
`HSTS`, `STATIC_CACHE`, `MEDIA_PERMA_CACHE`, `REPORT_PANICS` on, `SHOW_ERRORS`
off, `LOG_LEVEL=info`; `.env.example`, compose and the E2E harness turn them
off.

Not settings, left alone: test tooling read only by test code (`HEADED`,
`SLOWMO`, `CHROMIUM_PATH`, `UI_ARTIFACTS`, `GOCOVERDIR`, the golden
`UPDATE_GOLDEN`); `VERSION` (set in the Dockerfile, read by nothing);
`PCOM_WATCH_POLL` and `PCOM_*` tool switches (shell and compose only);
`PG*` variables that `lib/pq` reads (driver level). `godotenv/autoload`
stays: it fills the environment before go-flags reads it.

Hidden readers to remove: `config.LoadDefaultConfig` in the S3 storage reads
`AWS_*` variables and `~/.aws`; build the client from `s3.Options` instead,
so the `USER_MEDIA_*` settings are the whole S3 configuration.

**How "every variable is tested" is checked:**

1. `pkg/config`'s table test has one row per row above: set the variable,
   parse, assert the field; for required ones, set it empty and assert the
   error names `$VAR`; for `Secret`s, assert `%v` and `%+v` of the config
   don't contain the value.
2. A golden of `pcom --help` (and `serve --help`, `admin --help`): any rename,
   removal or new option shows up in the diff.
3. A completeness test walks the parser's options and fails on an `env:`
   key that has no row in the table test, so a new setting can't land
   untested.
4. `pkg/arch` gains a rule: no `os.Getenv`/`os.LookupEnv` in non-test code
   outside `cmd/web` (and `e2e/`, `pkg/testutil`). It starts with an
   allowlist of today's files, each task shrinks it, and F empties it.
5. Each behavior setting has an on/off test where it takes effect (task B),
   and the E2E harness configures the binary only through these variables,
   so the names are exercised end to end.

## Decisions for C0

- **D1 (decided 2026-09-30: production-safe). Defaults of the ex-`FLY_APP_NAME` booleans.** Recommended:
  production-safe defaults (`SECURE_COOKIES`, `HSTS`, `STATIC_CACHE`,
  `MEDIA_PERMA_CACHE`, `REPORT_PANICS` on; `SHOW_ERRORS` off), with
  `.env.example`, compose and the E2E harness turning them off. Production
  keeps working with its current secrets and nothing new in `fly.toml`, and a
  forgotten variable fails safe. The alternative (development defaults, the
  production values in `fly.toml [env]`) fails open if `[env]` is lost.
- **D2 (decided 2026-09-30: the tool in the image).** Migrations at deploy
  don't go through the binary, so `go.mod` keeps no migration library (the
  2026-09-28 decision stands). The Dockerfile's builder stage installs
  `sql-migrate` at the version pinned in `tools/Dockerfile` (one `ARG`, kept
  equal; `generate.sh`'s version check or a CI grep enforces it), and the
  final image gets `/usr/local/bin/sql-migrate`, `/dbconfig.yml` and
  `/migrations`. `fly.toml` gets
  `[deploy] release_command = "sql-migrate up -env=production -config=/dbconfig.yml"`;
  fly passes the app's secrets, so `DATABASE_URL` is there. The production
  `DATABASE_URL` has `?sslmode=disable` (fly's internal network), which
  sql-migrate uses as is. `make migrate-prod` stays as the manual fallback.
- **D3 (decided 2026-09-30: keep the guard). `seed` in production.** `seed` refuses to run when `FLY_APP_NAME`
  is set. Recommended: keep that guard as an option of the `seed` command
  only (`env:"FLY_APP_NAME"`, undocumented in `--help` of `serve`): it is a
  safety catch, not a behavior switch.

## tommy

tommy 0.3.0 covers R2 as is; no change is required:

- Mailjet: gogo's sender calls `SendMailV31`, and tommy's mailjet provider
  serves `POST /v3.1/send` on the ingress port (8822).
- Reading mail: use tommy's mail API, not raw events:
  `GET /api/v1/mail/messages?to=<addr>&subject=<s>` returns parsed messages
  (recipients, subject, `text`, `html`), newest first. `to` is a substring
  match, so `app.Mails` re-checks the exact recipient. Factory addresses are
  unique per test, so parallel tests sharing one container don't see each
  other's mail.
- S3: `TOMMY_S3_BUCKETS`, `GET /api/v1/s3/buckets/{b}/objects/{key}` for
  metadata, `/content/{key}` for bytes, `GET /api/v1/events?plugin=s3&type=s3.object.put`
  for the `X-Amz-Acl` header. Readiness: `GET /api/v1/health`.

Optional improvements to propose upstream, none blocking:

- **Event capacity from the environment** (`TOMMY_CAPACITY`, and per
  plugin). Retention is 500 events per plugin and settable only in the TOML
  file. One container serves a whole E2E package; if a run ever produces
  more than 500 S3 events (every media GET is one), an ACL assertion could
  lose its put event. Workaround without the change: mount a config file
  into the test container.
- **A stdlib Go client for the read-back API** (`tommy/client`: list and
  wait for mail by recipient, object metadata, events by type), alongside
  `clienthelp`. pcom's `testutil/tommy` would shrink to container startup;
  gogo could then offer `testcontainers/tommy` next to `testcontainers/postgres`.
- **An exact-match recipient filter** (`to_exact=` or `rcpt=`) on
  `/mail/messages`, so clients don't re-filter substring matches.

### C0

Contract work, done by the coordinator. Each package that has settings owns
a small config struct with go-flags tags (the pattern of gogo's
`mjconfig.Config`); `pkg/config` composes them into the root options and the
`serve` command and builds the parser (`flags.HelpFlag`, no
`PrintErrors`, parsed with `settings.Parse`). `main.go` shrinks to building
the parser and executing. `serve` passes each value on explicitly; packages
not yet converted keep their `os.Getenv`, allowlisted with the task that
removes it. Keep the `mediaServerCleanup` fix from #111 (check the error
before deferring).

### E

assertions. Every assertion that read the queue must keep checking the same
